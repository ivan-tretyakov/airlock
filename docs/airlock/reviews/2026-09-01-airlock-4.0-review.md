# Airlock 4.0 — Slim Core Spec Review

**Date:** 2026-09-01 · **Reviewed:** `docs/airlock/specs/2026-09-01-airlock-4.0-slim-core.md` (draft), branch `feat/herdr-adapter-spec`
**Baseline:** `main` at `aea7d7c` plus `3135f65` · **Method:** every removal-list name, migration claim, and output-contract statement checked against `scripts/airlock.mjs`, `scripts/airlock.test.mjs`, `commands/airlock.md`, `.opencode/command/airlock.md`, `roles/*.md`, `.claude-plugin/*.json`, `PROJECT-CONVENTIONS.template.md`, `README.md`, and the local/remote git tag and history state. The slim-down decision itself is not reviewed.

---

## Verdict

**Request changes.** The core of the spec (schema v4, budget mapping, dispatch simplification, keep-list) is sound and the v3→v4 `expensive` mapping is faithful to 3.x `isExpensive`. But two blockers make the spec unimplementable as written — the `UPGRADED` line breaks the machine-readable output contract, and removing `roles/` deletes the only source of OpenCode agent bodies without naming a replacement — and several removal/migration claims are contradicted by the actual repository state.

## Findings

### F1 — blocker — `UPGRADED` leading line breaks the machine-readable output contract

**Spec:** §"v3 read compatibility" ("Commands that read a v3 plan emit one leading line: `UPGRADED …`") and §"Host shims".

Every command writes exactly one payload to stdout: plain text, or in `--json` mode one JSON document (`output()`, `scripts/airlock.mjs:823-825`; the error path likewise emits a single `{"error": …}` document, lines 1355-1360). The spec does not say where the `UPGRADED` line goes:

- If it is prepended to stdout in `--json` mode, the output is no longer parseable JSON. The Herdr adapter and any `--json` consumer break on every v3 plan.
- If it precedes text output, `NOTHING TO DO` and `TASK <id>` are no longer the first line, breaking any first-line dispatch on the shim contract ("If it prints `NOTHING TO DO` …"). The spec's own `taskText` shape in §"Dispatch model" shows `TASK` as line one with no `UPGRADED` slot.
- Behavior on the error path is unspecified: does `next --unattended` on a v3 plan print `UPGRADED` before the `PARKED` error (exit 2)? Before a validation error?

**Resolution.** Specify: `UPGRADED …` is written to **stderr** in all modes (or, alternatively, becomes an `upgraded` field in `--json` output and a trailing line in text output). State explicitly that stdout's first line remains `TASK`/`NOTHING TO DO`/the JSON document, and that the note is emitted at most once per invocation including error paths. Add a `--json`-mode test to §Tests.

### F2 — blocker — OpenCode agent bodies have no source after `roles/` is removed

**Spec:** §"Dispatch model" ("`roles/` is removed as a separate directory; the agent files become the single source") and §"Routing removal".

`roleSource()` reads `../roles/<role>.md` (`scripts/airlock.mjs:921-934`); `roleBody`/`roleTools` feed `agentMarkdown`. The spec deletes `agentMarkdown` but never lists `roleSource`/`roleBody`/`roleTools` — under the removal list as written they survive and immediately break (the directory they read is gone).

More importantly, §Dispatch model requires `init --host opencode` to write `.opencode/agent/airlock-*.md` with **OpenCode** frontmatter (`mode: subagent`, `permission: edit: deny` for checker/browser, no `tools:` line), while the bundled Claude agents in `agents/` carry **Claude** frontmatter (`name`, `description`, `tools`). The spec never says where the OpenCode files' content comes from: read from `agents/*.md` with a defined frontmatter transform? A second packaged set? Inline string constants?

**Resolution.** Specify the packaged source explicitly, e.g.: `init --host opencode` reads `agents/airlock-<role>.md`, strips the Claude frontmatter via the existing `roleBody` mechanics, and emits OpenCode frontmatter (keep `roleSource`/`roleBody` retargeted at `agents/`, delete `roleTools` or keep it for the Claude generation step). Add the transform to the removal/keep list and note that `agents/` must be included in `package.json` `files` so the npm-installed OpenCode CLI can read it.

### F3 — major — `plugin.json` already registers agents; renaming and namespacing are unresolved

**Spec:** §"Dispatch model" ("`plugin.json` gains the `agents` entries if the plugin schema requires explicit registration; otherwise directory convention applies").

`.claude-plugin/plugin.json` already contains `"agents": ["./roles/builder.md", "./roles/checker.md", "./roles/browser.md"]`. It does not "gain" anything — deleting `roles/` without rewriting these three paths leaves the manifest pointing at missing files, failing `claude plugin validate --strict` (a command the README's Validation section instructs users to run). Additionally, those bundled agents are named `builder`/`checker`/`browser` in frontmatter, not `airlock-builder` etc., so today no subagent named `airlock-builder` exists anywhere in the plugin.

Second, the dispatch contract ("dispatch its TASK to its exact `AGENT`") requires that the identifier `airlock-builder` be the string a Claude Code session can dispatch to. In 3.x this held trivially because generated agents lived in `~/.claude/agents/`. Plugin-bundled agents may surface under a plugin-namespaced identifier; the spec asserts dispatchability without verifying that the plain frontmatter `name` is what the host resolves.

**Resolution.** State that `plugin.json`'s existing `agents` entries are rewritten to `./agents/airlock-builder.md` etc., that each file's frontmatter `name` is `airlock-<role>`, and add an acceptance step: install the plugin and confirm a `Task`/subagent dispatch to the literal string `airlock-builder` resolves (adjust the `AGENT` line format if the host requires a namespaced form).

### F4 — major — the Herdr freeze depends on a release that does not exist

**Spec:** §"Extensions" ("it stays available from the `v3.1.x` tags").

Verified against the repository: `git tag -l` and `git ls-remote --tags origin` list only `v3.0.0` and `v3.0.1`. No `v3.1.x` tag exists locally or on the remote (the README's `#v3.1.0` install tag is already dangling). Furthermore `extensions/` is untracked — `git log --all -- extensions/` is empty — so even if a `v3.1.x` tag existed today it could not contain the adapter. As written, "frozen at 3.x, available from the v3.1.x tags" freezes the adapter into nonexistence.

**Resolution.** Make the precondition explicit in §Versioning and migration: before 4.0 lands, commit `extensions/herdr` and cut/tag a `v3.1.x` release containing it (which also repairs the dangling `#v3.1.0` install instruction). Alternatively, reword the freeze to name the concrete commit/branch the adapter will live at.

### F5 — major — versioning misses `marketplace.json` and the shim's own install tags

**Spec:** §"Versioning and migration" ("`package.json` and `.claude-plugin/plugin.json` → `4.0.0`. README's global-install line moves to `#v4.0.0`.").

Two release surfaces are omitted:

- `.claude-plugin/marketplace.json` also declares `"version": "3.1.0"`. The 3.2 review (P1) already established the convention that all three manifests move together.
- The OpenCode shim itself instructs installation: `.opencode/command/airlock.md:6` says `npm install --global github:ivan-tretyakov/airlock#v3.1.0` and carries the `#v3.0.0` historical-tag sentence. The rewritten 4.0 shim must move to `#v4.0.0`, and the test suite pins these strings (`airlock.test.mjs:905` matches `/airlock#v3\.1\.0/`, `:911` matches the `v3.0.0` line). §Tests does not mention updating them.

**Resolution.** Enumerate `marketplace.json` in the version bump; state that the 4.0 OpenCode shim's install line moves to `#v4.0.0` (and decide whether historical tags remain listed); add the corresponding test-assertion updates to §Tests.

### F6 — major — `PROJECT-CONVENTIONS.template.md` still ships the risk taxonomy

**Spec:** §"README rewrite" (rewrites README authoring guidance only).

`PROJECT-CONVENTIONS.template.md` — a packaged, user-facing template — says "Default to `standard` risk … Use `complex` only for … Reserve `critical` for …; `budget.maxExpensive` caps it" and "Keep model routing in the local Airlock configuration". Under 4.0 every one of those sentences is wrong: `risk` is rejected by `validatePlan` v4 and there is no local routing. The spec never mentions this file, so it ships 4.0 guidance that instructs users to author invalid plans.

**Resolution.** Add `PROJECT-CONVENTIONS.template.md` to the rewrite list: replace the risk bullet with the `expensive` guidance, delete the routing bullet, keep the consolidated-checker and builder-run-acceptance bullets (per the "verbatim in spirit" instruction already given for the README).

### F7 — major — Claude model customization path points at plugin-managed files

**Spec:** §"Dispatch model" ("A user who wants a specific model per role edits the agent file locally").

For OpenCode this works: `.opencode/agent/*.md` are project files with a hash guard. For Claude Code the bundled agents live inside the installed plugin directory; edits there are overwritten on every plugin update and are not a sane customization channel. The 3.x codebase treated same-named project agents as an error (`assertRouteAgent` "project agent shadows local Airlock route", `scripts/airlock.mjs:590-592`); 4.0 deletes that guard, which silently flips shadowing from forbidden to the *intended* mechanism — but the spec never says so.

**Resolution.** Specify the Claude override path explicitly: a user creates `~/.claude/agents/airlock-<role>.md` (or project `.claude/agents/…`) with the same `name` and a `model:` line, which takes precedence over the bundled agent; note that the 3.x shadow guard is removed deliberately for this reason. Verify the host's actual precedence order before finalizing.

### F8 — minor — removal-list gaps leave dead code

**Spec:** §"Routing removal".

Checked every listed name against call sites; the list is accurate for what it names, but incomplete:

- `openCodeConfigDir` (`scripts/airlock.mjs:936`) — remaining callers are all deleted (`routeAgentPath:583`, `desiredHostAgents:974`, `syncHostAgents:1026`). Dead, not listed. Its `OPENCODE_CONFIG_DIR` env handling dies with it.
- `claudeAgentsDir` (`:945`) — callers `routeAgentPath`/`desiredHostAgents` only. Dead, not listed, along with `AIRLOCK_CLAUDE_AGENT_DIR`.
- `configText` (`:1156`) — only caller is the removed `config` command branch. Dead, not listed.
- `importLedger` (`:1127`) — the `import` command is removed in §Command surface, but no section lists the function itself for deletion (the §Routing removal list is explicitly routing-only, and nothing else names it).
- Nit-level: the `unlinkSync` and `readdir` imports become unused once `syncHostAgents` goes.

**Resolution.** Add `openCodeConfigDir` (unless retained per F2's OpenCode decision), `claudeAgentsDir`, `configText`, and `importLedger` to the deletion list.

### F9 — minor — `render` and `status --json` route plumbing not addressed

**Spec:** §"Routing removal" ("`ROUTE`/`FALLBACK` lines in `taskText`/`start`/`status`") and §"Dispatch model" ("JSON output for `next`/`start`/`status` drops `route` objects entirely and keeps `agent`").

- `renderMarkdown` (`scripts/airlock.mjs:915-919`) calls the deleted `routeFor` for its `| Route |` table column. `render` survives in §Command surface, but neither the column's fate nor its replacement (role only? `AGENT` name?) is specified.
- `statusText`'s DOING/NEXT rows embed `route.model`, `routeState`, and candidate counts (`:808-817`), not literal `ROUTE` lines; "ROUTE/FALLBACK lines in status" under-describes the change. Specify the 4.0 row shape.
- `status --json` currently returns `{text, plan, routes: […]}` and has no `agent` field, so "drops `route` objects and keeps `agent`" is not satisfiable for `status` as phrased. Specify whether the `routes` array is deleted outright or replaced by per-doing-task `{task, agent}` entries.

**Resolution.** Give the exact 4.0 shapes for `render --md`'s table, `statusText` rows, and `status --json`.

### F10 — minor — the 3.1 shim hash is not "already enumerated"

**Spec:** §"Host shims" ("the content hashes of the unmodified 3.1.0 shims (already enumerated in `LEGACY_OPENCODE_COMMAND_HASHES` plus the hash of the current packaged 3.1 shim) are replaced automatically").

Verified against `bootstrapOpenCode()` (`scripts/airlock.mjs:20-23, 1032-1051`): the set contains two 3.0-era hashes (`93a2…`, `e007…`); the current packaged shim hashes to `9201872f0c11c80d2a76b90bd14afc911943f7cf2923bd4212798a07eaba6e8e`, which is **not** in the set — today it survives the `--class <class>` probe instead. The parenthetical labels the enumerated hashes as "3.1.0 shims", inviting an implementer to believe the work is done and skip adding the 3.1 hash, after which unmodified 3.1 shims would hit the new manual-merge error instead of auto-upgrading. The replacement probe direction (customized shim must contain the 4.0 shim's distinguishing content to be left alone) is otherwise correct.

**Resolution.** Reword: "add the hash of the packaged 3.1 shim (`9201872f…`) to `LEGACY_OPENCODE_COMMAND_HASHES`, which currently holds only the two 3.0-era hashes." Keep the spec's existing test ("unmodified 3.1 shim auto-upgrades") — it catches this if worded to use the real packaged content.

### F11 — minor — explicit `expensive: false` is rejected; residual `risk` is unspecified

**Spec:** §"Plan schema v4" ("optional boolean `expensive` (default `false`, must be `true` when present)").

Two edges:

- `expensive: false` is semantically identical to the default yet fails validation. Nothing is gained by rejecting it, and hand-authors (and JSON generators that always emit the field) will trip on it. Either accept `false` as a no-op or keep the strict rule — but the spec should state the rejection message and add the `expensive: false` case to §Tests explicitly (the current test line only covers "must be boolean `true` when present" for non-boolean/true values).
- A v4 plan carrying a stray `risk` field is silently ignored by the validator style used throughout `validatePlan` (unknown fields are not rejected). An author migrating by hand who writes `"schema": "airlock.plan/v4"` but keeps `risk: "critical"` and omits `expensive` silently loses budget protection.

**Resolution.** Decide and state both: recommend accepting `expensive: false` as equivalent to absent, and rejecting any `risk` field on a v4 task with a message pointing at `expensive` ("task T1 risk was removed in v4; use expensive: true for critical-cost tasks").

### F12 — minor — stray `--host` on non-`init` commands: reject or ignore?

**Spec:** §"Command surface" ("`--host claude|opencode` remains **only** on `init`").

Both current shims pass `--host` to *every* command (`next`, `start`, `done`, `block`, `audit`, `status`, `answer`), and the OpenCode guard deliberately preserves customized shims — which keep passing `--host` until their owner reruns `init` and performs the manual merge. If 4.0 rejects the flag on non-`init` commands, every preserved shim breaks with an unrelated-looking error on its first `next`. `parseCli` collects flags generically, so silent acceptance is the zero-cost path.

**Resolution.** State that `--host` (and, for one release, `AIRLOCK_HOST`) is accepted and ignored outside `init`, or explicitly accept the breakage and say the error message must mention re-running `init --host opencode`.

### F13 — minor — v3 plans never persist through the read-only loop; `start` resume shape unspecified

**Spec:** §"v3 read compatibility" ("Any command that writes the plan persists the upgraded form") and §"Command surface".

Only `start` (fresh), `done`, `block`, `ask`, and `answer` call `writePlan`. A v3 plan driven by `next`/`status`/`audit`/`render` — or a plan whose sole remaining task is mid-`doing` and is resumed, since the `start` resume branch (`scripts/airlock.mjs:1218-1224`) returns without writing — stays v3 on disk indefinitely and emits `UPGRADED` on every invocation. That is workable but currently only implied; the "one leading line" phrasing reads as a one-time event. Relatedly, the spec never gives `start`'s 4.0 output shape: presumably `STARTED <id>` / `STARTED <id> (resume)` followed by `AGENT airlock-<role>`, with the `ROUTE` line deleted — the resumed-doing case is exactly the v3-migration path (its pinned route vanished), so its output deserves one explicit line in the spec.

**Resolution.** Either specify eager persistence (readPlan writes back the upgraded plan when the file is writable — simplest, makes `UPGRADED` truly one-time) or state that read-only invocations re-emit the note each time. Add the exact `start`/`start`-resume output lines to §Dispatch model, and a v3-resume test (mid-`doing` v3 plan → `start <id>` prints `STARTED <id> (resume)` + `AGENT`) to §Tests.

### F14 — nit — `UPGRADED` message is constant regardless of plan content

**Spec:** §"v3 read compatibility".

The fixed text `(risk: critical -> expensive)` is emitted even for v3 plans with no `critical` task, where nothing maps to `expensive`. Also unhandled: a v3 task that (invalidly for v3, but unvalidated pre-upgrade) already carries an `expensive` field — does the upgrade overwrite, reject, or ignore it? Recommend dropping the parenthetical or making it conditional, and stating that pre-existing `expensive` on a v3 task is rejected by the upgrade function.

### F15 — nit — `isExpensive(task) === task.expensive === true` chained equality

**Spec:** §"Plan schema v4". As JavaScript this parses `(isExpensive(task) === task.expensive) === true`, which is accidentally truthy in the wrong ways. Since the spec is the implementation reference, reword to `isExpensive(task)` returns `task.expensive === true`.

### F16 — nit — ceiling claim overstates the change; companion assertions unaddressed

**Spec:** §"Host shims" ("The tested 5,000-byte prompt-surface ceiling stays and now covers command shims plus bundled agent files") and §"Tests".

The current test (`airlock.test.mjs:877-911`) *already* sums `commands/` + `roles/` + `.opencode/command/` — the change is a rename of `roles/` to `agents/`, not a coverage expansion. Unaddressed alongside it: the 800-byte per-role ceiling (`:889-892` — kept for `agents/` files, which grow slightly from the `name:` rename?), and the shim content assertions that must flip from presence to absence (`--class <class>`, `fallback <id>`, `Never fallback after any child result`, `:893-900`). One sentence in §Tests settles all three.

## Verified claims (no defect)

- **Budget mapping is faithful.** 3.x `isExpensive` counts only `risk === "critical"` (`scripts/airlock.mjs:714-716`); the upgrade maps exactly `critical → expensive: true` and drops `light|standard|complex`, so `budgetState`/`selectNext` semantics are unchanged for upgraded plans, including previously-uncounted `complex` tasks.
- **`readPlan`/`writePlan` ordering holds.** Upgrading in memory before validation yields a v4 object; `writePlan` re-validates v4 and passes. The `done` rollback path restores the original raw bytes (v3), which is safe.
- **Every routing name in the §Routing removal list was confirmed deletable** — no surviving code calls any of them (gaps are the *additions* in F8). `contentHash`, `LEGACY_OPENCODE_COMMAND_HASHES`, `AIRLOCK_NOW`/`commandNow`, and `isCoordinatorPath`'s `.opencode/agent/airlock-` exclusion are correctly retained.
- **Plan discovery under `docs/airlock/` is unaffected** (`findPlan`, `scripts/airlock.mjs:88-101`).
