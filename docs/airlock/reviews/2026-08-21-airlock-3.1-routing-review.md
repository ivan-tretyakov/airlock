# Airlock 3.1 — Routing Proposal Review (pre-implementation)

**Date:** 2026-08-21 · **Reviewed:** `docs/airlock/specs/2026-08-21-airlock-3.1-routing.md` (approved plan, not implemented)
**Baseline verified:** 3.0.1 at `16b0e38` — suite 26 tests, 25 pass, 1 skipped (`owns folds case on case-insensitive hosts`, correctly platform-gated to win32/darwin)
**Method:** spec read against the 3.0.1 source; both hosts' agent-configuration schemas verified against current official documentation and source, not from memory. Facts and their sources are given inline.

---

## Verdict

**The design is sound and the scope discipline is right. Three things must change in the spec before code is written — all three come from host behaviour the spec assumes but that the documentation contradicts or leaves unverified.**

The single biggest risk is on the OpenCode side of effort. Tracing OpenCode's source shows `variant` **does** reach subagents, but only when the resolved model declares a variant of exactly that name — and the names are defined **per model**, not per host. Otherwise it degrades to the provider default with no error. All 24 planned tests would pass while the effort silently never applies.

## 1. What the research confirms is right

Three of the spec's least obvious choices are **correct, and now evidenced**:

**The generated-agent approach is not over-engineering — it is the only option on OpenCode.** OpenCode's `task` tool schema accepts `description`, `prompt`, `subagent_type`, `task_id`, `command`, `background` and **no model parameter**; the model comes from the target agent's config or falls back to the parent session's model. The feature request to add one ([issue #26536](https://github.com/anomalyco/opencode/issues/26536)) was closed as not planned. Pre-generating one agent per route is therefore the only way to get deterministic model selection on that host.

**`CLAUDE_CODE_SUBAGENT_MODEL` really does need the fail-closed check in §6.2.** It sits at priority 1 in Claude Code's model resolution — above the per-invocation parameter *and* above the subagent's own frontmatter. If it is set, every route Airlock computes is silently overridden. Refusing to run is the right behaviour and the spec is right to single it out.

**The restart requirement in §6.3 is real, not defensive.** OpenCode does not hot-reload agents; [issue #8751](https://github.com/anomalyco/opencode/issues/8751) exists precisely because it doesn't.

Also right: UTC-only with no DST conversion; overnight windows rejected rather than half-supported; the §2 non-goals (no quota modelling, no provider probing, no weighted rotation, no request-level failover) — that list is what keeps 3.1 from becoming a router. And acceptance criterion 13 requiring the suite to pass on Windows shows the M2 lesson from the 3.0 merge stuck.

## 2. 🔴 Must change before implementation

### P1 — OpenCode `variant` works, but only if the model declares that exact variant name — and it fails silently

**Correction to my earlier note:** I traced this in OpenCode's source rather than relying on the issue tracker. `variant` is *not* broken for subagents. It is conditional, and when the condition fails it degrades to default reasoning with **no error**.

The chain, from `anomalyco/opencode` at HEAD:

`packages/opencode/src/tool/task.ts:209`
```ts
variant: next.model ? undefined : variant,   // `variant` here is the PARENT session's
```
A subagent that declares its own `model` — which every Airlock-generated agent does — is dispatched with `input.variant === undefined`. It does not inherit the parent's variant. So far this looks like the agent's own `variant` is ignored. It is not:

`packages/opencode/src/session/prompt.ts:647-654`
```ts
const model = input.model ?? ag.model ?? (yield* currentModel(input.sessionID))
const same  = ag.model && model.providerID === ag.model.providerID && model.modelID === ag.model.modelID
const full  = (!input.variant && ag.variant && same) ? yield* provider.getModel(...) : undefined
const variant = input.variant ?? (ag.variant && full?.variants?.[ag.variant] ? ag.variant : undefined)
```

So the agent's `variant` **is** honoured, on three conditions — all of which Airlock satisfies except the third:

1. the dispatch passes no variant ✅ (guaranteed by `task.ts:209`);
2. the agent's declared model equals the resolved model (`same`) ✅ — **provided nothing overrides the model at dispatch**;
3. `full.variants[ag.variant]` exists — i.e. **the resolved model declares a variant with exactly that name**. ⚠️

If condition 3 fails, `variant` becomes `undefined`. No warning, no error, no trace in the brief. The route is deterministic; the reasoning effort is the provider default.

**And variant names are per-model, not universal.** From `packages/opencode/src/provider/transform.ts`, the name set is computed from each model's `models.dev` `reasoning_options` or a per-provider hardcoded table:

| Model class | Variant names available |
|---|---|
| `reasoning_options` type `effort` | that model's own effort values (`effortVariants`) |
| type `budget_tokens` | **only `high` and `max`** (`budgetVariants`) |
| toggle-only | `none`, `high` (`reasoningToggle`) |
| Google Gemini 2.5 | **only `high` and `max`**; newer Gemini uses `thinkingLevel` efforts |
| GLM-5.2 via OpenRouter | **only `high` and `xhigh`** |
| MiniMax-M3 | `none`, `thinking` |

So `effort: "medium"` — perfectly valid on Claude Code — silently no-ops on a budget-type or GLM OpenCode model. This is the same silent-degradation failure I flagged, arriving through a different door, and it means P3 below is worse than a per-host problem: **the effort vocabulary is per-model.**

**Spec change, and it is now mechanisable rather than experimental.** `config --sync --host opencode` must validate each route's effort against the resolved model's actual variant list and fail closed on a name that is not there. Three ways to get that list, in order of preference for a dependency-free CLI:

1. **Declare it once in the local config** — e.g. `"variants": ["high", "xhigh"]` alongside the model — and validate against that. No network, no OpenCode internals, self-documenting, and it forces the user to look the names up once.
2. Query the running OpenCode server's provider endpoint (it exposes model `variants`).
3. Read `models.dev`'s catalog `reasoning_options` directly. (I could not fetch `models.dev/api.json` from this container — likely off the egress allowlist — so treat this route as unverified.)

**What still needs you, and it is now two minutes rather than an afternoon:** open the OpenCode TUI and read the variant names it offers for each model in your routes — the run footer lists selectable variants per model (`cli/cmd/run/footer.ts`). Write those names down; they are the only legal values for `effort` on that route. If `glm-5.3` and `gpt-5.6-sol` do not both offer the same names, that alone proves the per-model point and settles the config shape.

Note also the second condition: because `same` requires the dispatched model to equal the agent's declared model, **anything that overrides the model at dispatch silently drops the variant too.** That is the OpenCode analogue of P2 — one more reason neither shim should pass a model at call time.

### P2 — The Claude shim must stop passing a model at call time

Claude Code's model resolution order is: (1) `CLAUDE_CODE_SUBAGENT_MODEL`, (2) **per-invocation `model` parameter on the Agent tool**, (3) the subagent's frontmatter `model`, (4) the main conversation's model. There is **no per-invocation `effort` parameter** — effort comes only from frontmatter.

The 3.0.1 Claude shim currently says: *"dispatch the printed block verbatim to the role it names with `Agent`, **using the model it names**."* If 3.1 generates `airlock-builder-<model>-<effort>` agents carrying both fields and the shim still passes a model at call time, two things go wrong:

1. The call-time model wins over frontmatter. If the two ever disagree — a stale brief, a config edit between `next` and dispatch — you get **the generated agent's effort applied to a different model**, which is not any configured route.
2. It leaves a model decision in the orchestrator's hands, which is exactly what acceptance criterion 2 forbids.

**Spec change:** §8.3 must state that the Claude shim dispatches the named `AGENT` **and passes no `model` parameter**. Add a test asserting the shim text contains no call-time model instruction. This is a one-sentence change that closes the last orchestrator-substitution path.

### P3 — `effort` is an unvalidated free string, and the valid sets differ per host

3.0.1 validates `effort` only as a non-empty string — there is no allowed-value set anywhere in `airlock.mjs`. The spec inherits that. But:

- **Claude Code `effort`:** `low` | `medium` | `high` | `xhigh` | `max` (frontmatter field, documented).
- **OpenCode:** variant names defined **per model** (see P1) — `high`/`max` for budget-type models, `high`/`xhigh` for GLM-5.2 on OpenRouter, the model's own effort values for effort-type models. There is no set common to all models.

So `effort` is not one field with one vocabulary. A typo (`hgih`) or a cross-host copy (`max` where the provider defines no such variant) produces a generated agent that loads and dispatches at default effort with no error. That is a silent violation of acceptance criterion 1 — the route is deterministic, its effect is not.

**Spec change:** validate `effort` per host against that host's known set at config-write and at `--sync` time, and fail closed on an unknown value. Add to the test plan: unknown effort rejected for each host.

## 3. 🟠 Should change

### P4 — Fail closed at `next`, not at dispatch

§6.4 says *"Dispatch fails clearly when the selected generated agent file is absent."* By then `next` has offered the task and `start` has flipped it to `doing` and consumed the clean-boundary check. The orchestrator's only recovery is `block`, which stashes to a recovery ref and burns the task — the wasted-cycle class that took two review rounds to eliminate in 3.0.

`next` already computes the exact agent name in step 6 of §4.2. It can `existsSync` the file at that moment. **Make a missing generated agent a `next`-time refusal** naming the exact `config --sync` command. `start` should re-check as a second gate.

### P5 — The pin file adds a second state store; put the route in the task row instead

§5.2 introduces `<git-common-dir>/airlock/router-state.json` with a composite key over worktree, plan path, task id and host, plus staleness rules, plus the temp-write-and-rename pattern, plus §5.3's upgrade-recovery path. That is a meaningful amount of new machinery, and 3.0's central achievement was that `airlock.plan.json` is the *only* authored state.

What the pin actually buys is protection against a config edit or window crossing between selection and dispatch. Note that §5.3 already concedes a route can be **reconstructed from `startedAt` plus the mapping** — which is true, because the resolver is a pure function of `(host, role, risk, timestamp, mapping)`. So the file's only irreplaceable job is surviving a mid-task *config* change.

A cheaper structure gets the same guarantee:

- `next` resolves and **previews** the route (read-only, per the 3.0 planner decision that `next` does not mutate).
- `start` resolves once, **writes `route: {model, effort, name, evaluatedAt}` into the task row**, and **emits the authoritative brief**.
- The shim dispatches the brief `start` printed, not the one `next` printed.
- Resume reads the route from the task row. `done`/`block` leave it in place as evidence.

That removes the state file, the key schema, the staleness rules and the upgrade path (a pre-3.1 `doing` task simply has no `route` and gets one on resume), and it makes the route part of the audit trail rather than something deleted on completion — which is more in keeping with 3.0 than a side file is. It also closes P2's stale-brief window structurally, because the brief the shim dispatches is the one written at pin time.

The cost is one extra plan write per task, and `next`'s printed route becoming explicitly a preview. Both look cheap next to what is removed. If the pin file is kept anyway, say in the spec *why* the task row was rejected, so the next reviewer does not re-raise it.

### P6 — Writing version 2 unconditionally locks out any 3.0.x install

§3.4 says *"New files created by Airlock 3.1 use version 2"* and *"Airlock 3.0 must reject version 2."* Both are correct in isolation. Together, on a machine pair where one host still runs 3.0.x and the config lives in a synced folder, the 3.0.x side hard-fails on **every** command — `readRoutes` throws `requires version 1` before anything else runs. Given this project's history with OneDrive-hosted config, that is a realistic scenario, not a hypothetical.

**Spec change:** write version 1 when no route has windows; emit version 2 only once a window is actually configured. Same fail-closed property, no gratuitous lockout.

## 4. 🟡 Worth fixing while the spec is open

**P7 — Use `agents/`, not `agent/`.** OpenCode's current directory is plural `agents/`; singular `agent/` is retained only for backwards compatibility. 3.0.1 writes singular (`airlock.mjs:595`) and §6.3 repeats it. Switch, and have `--sync` report if legacy singular files exist.

**P8 — The LiteLLM migration guarantees orphaned agents.** `agentName` slugs from `model` + `effort`. §10 step 5 converts aliases to direct provider IDs, so **every** generated agent is renamed, while §6.4 never prunes. The migration therefore ends with a full parallel set of dead `airlock-*` agents in the user's global config. §6.4's "reports stale" is necessary but not sufficient — add `config --sync --prune` (refusing to remove anything referenced by a live route) or make §10 include an explicit removal step with the exact list.

**P9 — Specify the midnight boundary.** Ends are exclusive and overnight windows are rejected, so "until midnight" needs a representation. Is it `22:00-24:00`? `22:00-00:00`? The test plan checks `05:59/06:00/09:59/10:00` and never a day edge. Pick one, state it, test it — and make the overnight rejection message name the two-window workaround explicitly, since that is the first thing a UTC+2 user will hit.

**P10 — `~/.claude/agents/` is user scope, visible in every project.** Generated agents will appear in the agent list of every Claude Code project on the machine, and a project-level `.claude/agents/<same-name>.md` **silently takes precedence** over the user-level one. That is a live path for something other than Airlock's route to be dispatched under Airlock's name — acceptance criterion 2 again. Have `--sync` (and ideally `next`) detect a project-level file shadowing a generated agent and refuse.

**P11 — Mark preview versus pin in text output, not only JSON.** §7.2 puts `pinned|previewed` in the JSON. `status` mixes a pinned route for the `doing` task with a current-time preview for the next todo — two time bases in one view. The human-readable output is what the user actually reads at the single consolidated prompt; label it there too.

**P12 — Note the OpenCode moving target.** The repository has moved to `github.com/anomalyco/opencode`, and an OpenCode 2.0 config format is in beta with a documented v1→v2 migration. 3.1 hard-codes the v1 agent schema. That is the right call today, but the spec should record the assumption and the doc URL it was verified against, so the next break is diagnosable rather than mysterious.

## 5. ⚪ Carry-over from 3.0

**The `v3.0.0` tag still does not exist.** `git tag -l` on `origin/main` returns nothing, while `README.md` instructs `npm install --global github:ivan-tretyakov/airlock#v3.0.0`. This was gate M1 of the PR #6 verification. §8.4 of the 3.1 plan says to "update tagged installation examples" to 3.1.0 — which would leave two versions of a broken install command. Create `v3.0.0` (and later `v3.0.1`) before, or as part of, the 3.1 work.

## 6. Token efficiency and wasted cycles

**Prompt surface: effectively unchanged.** Routing adds one `ROUTE <name> | evaluated <ts>` line to each brief and an `AGENT` line on the Claude side — a few dozen bytes per dispatch. The shims gain one clause each. Current surface is 3,814 B against the 5,000 B ceiling; 3.1 should land near 3,900 B. Keep the ceiling test.

**The real efficiency argument for 3.1 is not prompts, it is model selection.** Deterministic per-role/risk effort means `light` work stops paying `high`-effort reasoning, and scheduled windows let expensive providers be used only when their quota is fresh. That is a larger lever than anything in 2.3–3.0 touched. It is worth stating that in §1 as the actual motivation, because §1 currently frames the goal as determinism and hides the payoff.

**Wasted cycles: one new risk, P4.** Everything else in the plan is selection logic that either resolves or fails closed before work starts. P4 is the one path where a routing error costs a task rather than a command, which is why it deserves the `next`-time gate.

**Testing:** the plan's 24 items are well chosen — boundary inclusivity, one-timestamp-per-command, pin stability across config change, deduplication, missing-agent failure. Gaps to add: unknown `effort` per host (P3); midnight boundary (P9); a shim assertion that no call-time model is passed (P2); an assertion that no real user mapping exists in the repo (acceptance 11 is currently unenforceable — note 3.0.1 already removed `.airlock/models.json`, so this is about keeping it that way).

---

## 7. Recommendation

Proceed, with the spec amended for P1–P3 first and P4–P6 decided before code. P1 is now a concrete design change rather than an open question: effort must be validated against a **per-model** list of legal variant names, declared in the local config, and `--sync` must fail closed on anything else. The only manual step left is reading the legal variant names for your two OpenCode models out of the TUI footer.

The shape of 3.1 is right: routing is data, resolution is a pure function, the orchestrator gets a name and dispatches it. That is the same principle that made 3.0 work — validate the plan, not the tool call — applied to model choice.
