# Airlock 3.0 — Implementation Review

**Date:** 2026-08-20 · **Reviewed:** uncommitted working tree on `main` (19 new, 56 deleted, 5 modified) — not committed, no PR
**Baseline:** 2.6 as merged (`0036349`) · **Against:** `docs/airlock/specs/2026-08-20-airlock-3.0-design.md` incl. the §4.1 amendment
**Method:** working tree staged and reproduced in a Linux container (Node 22); the suite executed; seven adversarial scenarios run end-to-end against real git repositories. Every finding below was reproduced, not inferred.

---

## Verdict

**The architecture is right and the deletion is real. The lifecycle is not shippable yet: four reproducible failures stop a run dead, and three of them are the same class of deadlock that 2.6 died of.**

The good news is that all four are small, local fixes in one file. None of them challenges the design.

**Two things exceed the spec and are worth keeping.** `done` creates a real git commit with an `Airlock-Task:` trailer, and `next` uses that trailer to hand a `checker` the actual diff of its dependency. That is the review bundle rebuilt out of git alone, host-neutral, for free. And `start` enforces a clean worktree, giving every task a genuine boundary. Both are good ideas — R1/R2/R3 are all consequences of these two additions being incompletely wired, not of the ideas being wrong.

## 2. Blockers

### R1 — 🔴 The first run always deadlocks on the file `init` just wrote

`airlock init` creates `.airlock/models.json`. `airlock start` calls `assertCleanBoundary`, which counts every untracked path except the plan file. Reproduced verbatim:

```
$ airlock init "Ship a thing" --done "yarn test passes"
INITIALIZED /tmp/p1/airlock.plan.json
$ airlock next
TASK T1 · builder · sonnet        ← the brief is printed, so the model believes it is going
$ airlock start T1
task boundary requires a clean worktree; found: .airlock/models.json     ← exit 1
```

Every new project hits this on its first task, after `next` has already promised the work. Nothing in either shim recovers.

**Fix:** exclude Airlock's own state (`airlock.plan.json`, `.airlock/**`) from `dirtyProductPaths`, not just the plan file. `init` should also `git add` what it creates.

### R2 — 🔴 One failed audit halts the entire run — the 2.6 deadlock, rebuilt

The single most common builder mistake is touching one file outside `owns`. The shim's prescribed response is `airlock block <id>`. `block` records a note and changes nothing on disk, so the stray file stays — and every subsequent `start` refuses forever:

```
$ airlock start T1                 → STARTED T1
  (builder writes src/T1.js and STRAY.md)
$ airlock audit T1                 → OUT OF SCOPE: STRAY.md            exit 1
$ airlock block T1 --reason "..."  → BLOCKED T1
$ airlock next                     → TASK T2 · builder · haiku          ← still offers work
$ airlock start T2
task boundary requires a clean worktree; found: STRAY.md, src/T1.js     ← exit 1, permanently
```

This is precisely the failure you asked 3.0 to eliminate, and it defeats §4.1 directly: the run cannot "keep working", because the cheapest, most frequent error is now fatal to the whole session rather than to one task.

**Fix:** `block` must leave a clean boundary. Either stash the task's worktree state onto a `airlock/blocked/<id>` ref before recording the block, or make `block` refuse unless the tree is clean and tell the orchestrator to run `audit --revert-out-of-scope` first (see R6 before doing that). The stash form is safer and keeps the evidence.

### R3 — 🔴 A failed commit silently reports success

`done` writes `status: "done"` to the plan **before** calling `taskCommit`. If the commit fails — pre-commit hook, lint gate, missing `user.email`, commit signing, a protected-branch hook — the plan keeps the `done`, no commit exists, and the state is unrecoverable through the CLI:

```
$ airlock done T1 --evidence "node --test: pass"
lint failed                                    ← exit 1
$ <plan>  →  status: done, evidence: ["node --test: pass"]
$ git log →  only the baseline commit
$ airlock done T1 --evidence "retry"
task T1 cannot complete from done              ← no retry path
$ airlock next
NOTHING TO DO / All tasks are done.            ← reports success
```

An unattended run finishes "clean" with the work uncommitted in the worktree — and, thanks to R1's rule, the next delivery cannot start. Of the four, this is the one that produces a wrong answer rather than a stuck one.

**Fix:** commit first, then write the plan. `taskCommit` already re-audits, so ordering it before the state write costs nothing. Failure then leaves the task `doing` and retryable.

### R4 — 🔴 `node scripts/airlock.mjs` does not resolve where the plugin actually runs

Both shims invoke the CLI by a **repository-relative** path. Airlock ships as a marketplace plugin, so in any consuming repo `scripts/airlock.mjs` does not exist; and even inside this repo it fails from any subdirectory:

```
$ cd src/deep && node scripts/airlock.mjs status
Error: Cannot find module '/tmp/p2/src/deep/scripts/airlock.mjs'
$ cd /tmp/consumer && node scripts/airlock.mjs next
Error: Cannot find module '/tmp/consumer/scripts/airlock.mjs'
```

2.x got this right everywhere — `hooks/hooks.json`, `EXTERNAL-RUNTIME.md` and every command used `${CLAUDE_PLUGIN_ROOT}/...`. 3.0 dropped the convention along with the hooks. As it stands, 3.0 only runs when you are dogfooding from the airlock repo root, which is exactly the case the tests cover — hence 9/9 green while the shipped path is broken.

**Fix:** `node "${CLAUDE_PLUGIN_ROOT}/scripts/airlock.mjs"` in `commands/airlock.md`. OpenCode has no such variable, so the OpenCode shim needs either an absolute path written by setup or an `airlock` bin on PATH (`package.json` already declares one — use it, and document `npm i -g` / `npm link` in the README).

## 3. Major

### R5 — 🟠 The checker is handed the wrong diff once you have ten tasks

`dependencyContext` finds a dependency's commit with `git log --grep "Airlock-Task: T1"`. That is an unanchored substring match, so it also matches `Airlock-Task: T10` — and `-1` returns the *most recent* match. Reproduced with T1 and T10 both committed:

```
EVIDENCE T1  ev-T1                 ← correct
DIFF T1
  ... contents of T10's commit ... ← wrong
```

A checker verifying T1's acceptance against T10's diff will pass or fail for reasons unrelated to the task, and nothing in the output reveals it. This is the exact failure mode the review bundle existed to prevent.

**Fix:** `--grep "^Airlock-Task: T1$"` (git anchors per line), or record the commit SHA on the task at `done` and use it directly — better, since it survives history rewrites.

### R6 — 🟠 `audit --revert-out-of-scope` permanently deletes untracked files

For untracked paths the revert path is `rmSync(absolute, { force: true, recursive: true })`. There is no git copy, so the deletion is unrecoverable:

```
$ ls notes/  →  my-scratch.md
$ airlock audit T1 --revert-out-of-scope
$ ls notes/  →  (empty)      ← gone, not in any commit or stash
```

This matters more than it would in isolation, because `--revert-out-of-scope` is the obvious thing a stuck user reaches for once R2 bites. A user's unrelated scratch file, a `.env`, or a half-written note in the repo is destroyed by a scope-control command.

**Fix:** stash instead of delete — `git stash push --include-untracked -- <paths>` onto a named ref, or move to `.airlock/reverted/<timestamp>/`. Keep `rmSync` only behind an explicit `--force-delete`.

### R7 — 🟠 The `goal` blocking case is unreachable

`ask` requires an existing task id as its first positional argument:

```
$ airlock ask "Is the goal right?" --options "a|b" --blocking --case goal
unknown task: Is the goal right?
```

But §4.1's fifth blocking case is "the goal itself is ambiguous — `done` cannot be made testable", which by definition arises **before** tasks exist. The CLI accepts `--case goal` and then makes it impossible to use.

**Fix:** allow a plan-level decision with `blocks: []`, or accept `--task <id>` as optional and treat an absent task as goal-level.

## 4. Medium

### R8 — 🟡 The budget is decorative

`budget.maxExpensive` is validated on every read and used nowhere. `maxTasks` is only a cap on plan size, not on execution. Yet both shims end with *"Repeat until `NOTHING TO DO` or the task budget is reached"* — an instruction the model cannot follow, because nothing reports budget state. For an orchestrator meant to run unattended this is the one guard rail that should exist.

**Fix:** make `next` count `done`-since-session or `done` total against `maxTasks` and emit `BUDGET REACHED`; enforce `maxExpensive` as a cap on tasks resolving to the `critical` model. Or delete both fields — but do not ship an instruction that references them.

### R9 — 🟡 `--unattended` is unreachable

Implemented in `next`, mentioned in neither shim and in no `argument-hint`. The scheduled/remote workflow you designed the Linux box for cannot be invoked.

### R10 — 🟡 Every checker brief opens with plan-file churn

`taskCommit` commits `airlock.plan.json` together with the product changes, so `git show` of a dependency leads with ~40 lines of status/timestamp JSON before any code. Observed in the R5 repro. On a 12,000-character diff budget that is pure token cost, and it invites the checker to reason about bookkeeping.

**Fix:** `git show -- <task owns paths>` in `dependencyContext`, or commit the plan separately with a `chore(airlock):` message.

### R11 — 🟡 The OpenCode role→agent mapping is implicit

`next` prints `builder` and `zai-coding-plan/glm-5.3`. `opencode.json` defines `airlock-builder-glm` and `airlock-builder-sol`. The `glm`/`sol` suffix convention appears nowhere in the shim, the README, or `models.json` — the model is expected to infer it. It happens to work with two providers; it will not survive a third, and a mis-inference dispatches to the wrong model silently.

**Fix:** have `next --host opencode` print the resolved **agent name**, not the model string. The CLI already knows both.

### R12 — 🟡 `--parallel` is unusable with glob `owns`

`ownsOverlap` returns `true` whenever either side contains `*` or `?`, without comparing them. Any two tasks that use globs are treated as overlapping, so the parallel path never opens. Conservative and safe, but it means the spec's parallel provision is effectively dead. Worth either implementing prefix comparison or documenting the limitation.

## 5. Token efficiency and wasted cycles

**Prompt surface: excellent, and now structurally defended.** 3,302 bytes against a 5,000-byte asserted ceiling, down from 78,408. The per-dispatch brief is ~350 bytes; `status` ~200. The 33 KB CLI never enters a prompt. This is the single biggest win in Airlock's history and the ceiling test is what keeps it.

**Wasted cycles: currently worse than 2.5, for a fixable reason.** R1, R2 and R3 each convert a routine event — first run, one stray file, one lint hook — into an unrecoverable session. The token cost of a deadlock is not the failed command; it is the user restarting, the model re-reading, and the work being redone. Three of the four blockers are one-line ordering or filter changes, so the fix-to-value ratio here is the best it has been across 2.3–3.0.

**Two live token leaks after the blockers:** R10 (plan churn in every checker diff) and the flat 12,000-character diff slice in `dependencyContext`, which has no relation to what the checker's acceptance actually needs.

## 7. What to keep, unchanged

The deletion is the achievement: 56 files removed, no host-specific enforcement, one authored artifact, three roles, one command. `audit` catching a shell-created write — the case the 2.x hook never saw — is tested and passing. The assumption machinery from §4.1 landed exactly as designed, including `consumedBy` tracking and atomic rework on an overturned answer, which is the part I expected to be shaved. Resist the temptation to re-add a hook when R2 is fixed; R2 is a bookkeeping bug, not evidence that prediction-based enforcement was needed.
