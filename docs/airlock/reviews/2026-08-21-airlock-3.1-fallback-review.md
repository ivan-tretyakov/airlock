## 1. Verified working

Reproduced, not inferred from test names.

**The chain resolves, advances once, and exhausts cleanly.**

```
$ airlock start T1 --host claude
AGENT airlock-builder-haiku-medium
$ airlock fallback T1 --host claude --reason "rate limit"
FALLBACK T1 · candidate 2/3
TASK T1 · builder · sonnet · high
AGENT airlock-builder-sonnet-high
FALLBACK 1 airlock-builder-opus-max · opus · max
$ airlock fallback T1 --host claude --reason "timeout"
FALLBACK T1 · candidate 3/3
$ airlock fallback T1 --host claude --reason "again"
NO FALLBACK for T1: route default exhausted 3 candidates
```

**Every candidate agent is generated up front** — `config --sync --host claude` produced all three of `haiku-medium`, `sonnet-high`, `opus-max`, satisfying acceptance 6.

**The worktree audit refuses correctly**, with a message that names the file and the remedy:

```
refusing fallback for T1: failed attempt left changes in src/T1.js; block or recover the task before redispatch
```

**Router state v2 is a good design.** It keeps the complete chain, `candidateIndex`, and a failure log with reason and timestamp per failed candidate. **`fallback` on a non-`doing` task is refused** (`task T1 cannot fallback from done`). **Version 3 is opt-in** — `airlock config` still writes `version: 1` for a static route, so the older-binary lockout only bites once fallbacks are actually configured. **Claude briefs now carry `AGENT`**, which was OpenCode-only before.

**Previous round's items closed.** The catalog error is now exactly the actionable form:

```
OpenCode model openai/gpt-5.6-luna does not declare variant high in local catalog.
Add it under catalog.opencode["openai/gpt-5.6-luna"].variants in /root/.config/airlock/models.json.
Discover the legal names with: opencode models openai --verbose
```

## 2. 🔴 H1 — The parent spec now forbids the feature that shipped

`docs/airlock/specs/2026-08-21-airlock-3.1-routing.md` was modified **after** the amendment was written (mtime 1787310537 vs 1787309759), and it still says:

- §2 Non-Goals, line 27: *"implement request-level retries, failover, or model switching"*
- §2 Non-Goals: *"switch a model after an Airlock task has been dispatched"*
- §11 Acceptance, criterion 14: *"No quota, weighted-routing, provider-probing, or request-level fallback code is added."*

`airlock fallback` switches the model after dispatch. The amendment does not reconcile this; it sits alongside as a separate document. The two specs are now in direct conflict, and the routing spec is the one an implementing session is most likely to read first — a future agent following it would conclude the feature must be deleted.

**Fix:** amend §2 and criterion 14 to carve out the audited, operator-triggered, single-step fallback explicitly, and cross-reference the amendment from the routing spec. State what is still forbidden (automatic retries, health probing, cooldowns, quota tracking, weighted rotation) so the boundary stays legible.

## 3. 🟠 Major

### H2 — Nothing durable records which model actually did the work

After a task completes, the commit is:

```
T1: do T1

Airlock-Task: T1

Evidence: node --test: pass
```

No route, no model, no candidate index. The plan's task row has no `route` field. The pin — which holds the full chain and the failure log — is deleted at `done`.

Before fallback this did not matter: the route was a pure function of `(host, role, risk, timestamp, mapping)`, so it could always be reconstructed after the fact. **Fallback introduces runtime nondeterminism that configuration cannot reproduce** — which model produced a given commit now depends on how many dispatch failures happened that day. The audit trail loses exactly the information the new feature makes unpredictable.

This matters for the stated purpose: if `light` work quietly finishes on `opus` twice a week because the cheap candidate is rate-limited, nothing in the repository or the plan will ever show it.

**Fix consistent with your privacy stance** (the same objection that correctly killed the task-row route in P5): do not delete the pin at `done` — move it to a `completed` section of `router-state.json` keyed by task id and commit SHA. It stays local, never enters a tracked file, and remains greppable. A commit trailer would also work and be more visible, but reopens the model-leakage objection, so it should be an explicit choice rather than a default.

### H3 — The fallback trigger is prose the orchestrator must judge

The shim asks the model to classify a dispatch failure:

> If `Agent` errors before returning any child result due to provider auth, rate limit, timeout, transport, or model availability, run `… fallback …`. Never fallback after any child result, for cancellation, permission/configuration errors, or after Airlock refuses because changes exist.

That is a five-versus-four classification performed by the orchestrator with no mechanism behind it. The worktree audit is a genuinely good backstop, but it only catches a child that **wrote files**. It does not catch the case that matters most: a child that ran, reasoned, burned tokens and returned *"I can't do this"* being re-dispatched to a larger model. That is model-shopping — retrying a refusal until something complies — and given this project's history it is the failure mode most worth designing against.

**Fix, idiomatic to this codebase:** make `fallback` require `--class {auth|rate-limit|timeout|transport|model-unavailable}` from a closed set, exactly as `ask --blocking --case` already does for decisions. `--reason` stays free text. The class lands in the failure log, so a misuse pattern becomes visible in `router-state.json` instead of invisible. Consider also a per-task cap (two advances) so an exhausting chain cannot silently walk every task to the top of the ladder.

## 4. 🟡 Medium

**H4 — The cost guard and fallback disagree.** `isExpensive(task, root, host)` is now `return task.risk === "critical"` — declared risk, not the model actually dispatched. A `light` task whose chain ends on `opus/max` never counts against `maxExpensive`. Fallback can escalate any task to the most expensive model in its chain with no budget accounting at all. Either resolve expensiveness from the active candidate, or state in the spec that the budget governs declared risk only and fallback is deliberately outside it. (Minor: `isExpensive` takes `root` and `host` and uses neither.)

**H5 — Prompt surface is at 94% of the ceiling.** 4,682 B against 5,000. The trajectory across this release: 3,302 → 3,844 → 4,008 → **4,682**. The Claude shim alone is 1,807 B and most of the recent growth is H3's judgement clause — the class of prose 3.0 existed to remove. 318 B of headroom means the next feature breaches the ceiling and forces a rushed decision. Adopting H3's `--class` would let the shim shrink, because a closed set documents itself.

Related and worth an explicit decision rather than drift: the 3.0 design set a hard cap of **7 verbs**, with *"a new verb requires deleting one."* README now lists eight coordinator verbs — `next`, `start`, `fallback`, `done`, `block`, `ask`, `status`, `audit`. Nothing was deleted. `fallback` may well be worth the eighth slot, but the cap should be formally raised or the rule retired, not quietly exceeded.

## 5. Token efficiency and wasted cycles

**The feature's own economics are sound.** A fallback costs one CLI call and one re-dispatch; there is no retry loop, no probing, no polling. Each advance is explicit and bounded, and the exhaustion path terminates. This is a much cheaper design than LiteLLM-style failover, and it is the right shape.

**Source 65,188 → 72,383 B (+11%); tests 43,346 → 55,747 B (+29%).** The test-to-source ratio continues in the right direction, with named coverage for chain pinning, single-advance, worktree refusal, parallel-lane rendering, pruning protection, and version compatibility.

**The two efficiency risks are H4 and H2 together.** Fallback can silently promote cheap work to expensive models, the budget will not notice, and no record survives to let you find out later. That combination could quietly undo the cost control this whole release was built for — which is worth fixing before the first unattended run, not after.

## 7. Note

Nothing in the mechanism broke under probing — the chain, the audit refusal, the exhaustion path, the pruning protection and the candidate generation all did exactly what the amendment says. The findings are all at the seams: a spec that was not updated, an audit record that was not extended to cover new nondeterminism, and a trigger that was specified in prose rather than in a closed set. That is a good failure profile, and the fixes are small.
