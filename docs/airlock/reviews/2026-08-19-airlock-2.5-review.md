**Date:** 2026-08-19 · **Reviewed:** uncommitted working tree on `main` (14 files), version already `2.5.0` · 2.4 merged as PR #3 (`b55cf52`)
**Against:** `docs/airlock/specs/2026-08-18-airlock-2.5-design.md`
**Method:** working tree extracted and inspected directly; all four suites run (Linux, Node 22); prompt surface measured file-by-file across 2.3 → 2.4 → 2.5; gate/route table widths compared.

## Verdict

**Spec fully implemented, two items beyond spec, no functional defects found. Nothing blocks the merge.**

All recommendations below are improvements to *cost*, not correctness. R1 and R2 are worth doing in this release because they are cheap and they protect the release's own thesis; R3–R5 are follow-ups.

## The cost picture — read this before merging

**Cycles: genuinely improved.** Deterministic gates no longer create dispatches, independent verification collapses to pack-level, expensive leaves are rationed, and `code-complex` drops from opus to sonnet. Per Full pack of N Crossings the dispatch shape moves from ~3N to ~N+1, with opus confined to rows naming a criterion. This is the largest per-dispatch saving in any release so far.

**Prompt tokens: worse again — third release in a row.**

| Measure | 2.3 | 2.4 | 2.5 | Δ 2.5 |
|---|---|---|---|---|
| `commands/start.md` | 14,118 | 16,190 | 17,339 | +1,149 |
| `commands/plan.md` | 18,879 | 19,142 | 21,277 | **+2,135** |
| `commands/ship.md` | 13,982 | 14,014 | 14,225 | +211 |
| `commands/review.md` | 9,054 | 9,725 | 9,725 | 0 |
| `agents/orchestrator.md` | 10,254 | 9,239 | 9,933 | +694 |
| `references/LIFECYCLE.md` | — | 5,527 | 5,901 | +374 |
| **Total** | **66,287** | **73,837** | **78,400** | **+4,563** |

Two structural costs are worse than the byte count implies, because they multiply per row in every plan, permanently:

- the **gate table grew from 9 to 12 columns**;
- the **route table now carries 11 columns**.

A six-gate plan pays the wider gate table six times. The trade is still clearly positive — one avoided dispatch outweighs ~1K of prompt many times over — but the drift is now a pattern, and the measurement gate will not surface it because dispatch savings dominate the totals.

## Recommendations

### R1 — Add a prompt-surface ceiling and test it (do in this release)

The three-release drift (66.3K → 73.8K → 78.4K) has no mechanical brake. Add a `plugin-policy.test.mjs` assertion that the combined byte count of `commands/*.md` + `agents/orchestrator.md` + `references/LIFECYCLE.md` stays **at or below 80,000 bytes**. Current value is 78,400, so the next release of this size fails the suite — which is exactly when you want to be told, rather than discovering it in a usage report a month later.

The test helper already reads files via `source()` / `readFile`, so this is a few lines. State the number and its rationale in a comment so a future release raises it deliberately rather than by reflex. This is the same deny-only, mechanical-enforcement pattern that fixed ledger hygiene in 2.4 — a soft rule that failed under load became a hard check.

### R2 — Collapse the duplicated table columns (do in this release; recovers most of the +2,135)

`plan.md:103-105` now carries both `Executed by` and `Executor host role`, and the example row fills them identically (`implementer | implementer`). They encode the same fact at different granularity. Similarly, the route table's `Named criterion` duplicates what the `Why / independence` cell would naturally state.

- Merge `Executor host role` into `Executed by` — keep the three-value vocabulary, and let the row's `Execution reason` name a specialised role (browser-verifier, visual-verifier) when relevant.
- Merge `Named criterion` into the route table's `Why / independence` cell, keeping the A2 rule that a Complex/Critical row is invalid unless the criterion is named there.

That removes two columns from tables that repeat per row, without deleting a single rule. Keep the `plugin-policy` assertions — retarget them at the surviving column.

### R3 — Verify the release's own thesis on the first real deliverable (not in the suite)

The policy tests prove the wording exists; they cannot prove the behaviour changed. The whole release depends on plan authors actually writing `implementer` / `orchestrator-inline` and classifying **Standard**. If plans default to `independent` and Complex out of caution — the exact asymmetry A1–A3 were written to break — the prompt cost is paid for nothing.

On the first Full deliverable after merge, check spec acceptance criteria 1 and 3 by hand:

- a 3-Crossing pack produces **≤1** `independent` gate row;
- an ordinary contained change classifies **Standard** and dispatches `worker`/`code-standard`, not `code-complex`.

Record the result in the ledger. If either fails, the fix is tightening A2/A3, not adding more prose.

### R4 — Make the weight budget self-checking

A3 permits exceeding the budget with one PROGRESS line. That escape hatch is correct, but it can quietly become a rubber stamp. Add to the measurement note: in the first weekly `ai-usage.py` reading after merge, record **the share of dispatches on the expensive tier** and **the count of budget-exceedance PROGRESS lines**. If the expensive-tier share does not fall while exceedance lines are frequent, the budget is nominal — tighten the limit rather than adding rules.

### R5 — Windows verification before the PR (unchanged from 2.4)

Run all four suites on the Windows host and record the result. The `run-external-agent` effort-allowlist and wall-clock tests still have never been observed passing on any host; the Linux failures are environmental but that is an inference, not evidence.

## Note for the record

Two things this release got right that are easy to undervalue: `code-complex` defaulting to `sonnet` (the single largest per-dispatch cost reduction to date, and it required accepting that "complex" and "expensive model" are different axes), and the OpenCode dispatch block on model mismatch — which turns a silent capability downgrade into a stop. Neither was strictly required by the spec.
