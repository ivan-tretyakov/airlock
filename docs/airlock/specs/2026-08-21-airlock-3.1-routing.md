# Airlock 3.1 Deterministic Host-Specific Routing Plan

**Status:** implemented, pending merge
**Date:** 2026-08-21
**Baseline:** Airlock 3.0.1 at `16b0e38`
**Release target:** Airlock 3.1.0

**OpenCode variant gate:** passed on 2026-08-21. Two generated `openai/gpt-5.6-luna` subagents differed only by `variant: low` versus `variant: high`. OpenCode resolved and persisted the requested variants on the direct child responses, and `opencode models openai --verbose` reported `reasoningEffort: low` and `reasoningEffort: high` for those exact Luna variants. The responses recorded different reasoning usage (2,342 versus 1,759 tokens); token count is stochastic and is not expected to be monotonic in one sample. The high run returned the verified answer while the low run did not. The generated-agent `variant` design stands; 3.1 must additionally reject variant names that the selected model does not declare.

## 1. Goal

Add deterministic model, effort, and optional UTC time-window routing to Airlock 3.x without putting the user's actual model mapping in the Airlock repository.

Airlock, not the orchestrator, must select the exact route before dispatch. Claude Code and OpenCode must have independent mappings and may use different levels of routing complexity:

- Claude Code may use simple static role/risk mappings.
- OpenCode may use default routes plus UTC schedule windows.
- Either host may use scheduled routes later without another schema change.

## 2. Non-Goals

Airlock 3.1 will not:

- estimate provider credits, tokens, subscription balances, or reset windows;
- query provider billing or private dashboard APIs;
- implement weighted rotation, quotas, pause/resume, or expiration dates;
- implement request-level retries, failover, or model switching;
- manage credentials or provider authentication;
- replace LiteLLM for applications other than Airlock;
- switch a model after an Airlock task has been dispatched;
- commit any real user model assignment to this repository.

## 3. Local Configuration

### 3.1 Location and precedence

Mappings remain local:

1. User mapping: `~/.config/airlock/models.json`, or the existing platform-specific/configuration environment override.
2. Optional project override: `<git-common-dir>/airlock/models.json`.

The project override remains outside the tracked worktree. A project role/risk entry replaces the complete corresponding user entry. Windows are not partially merged.

One file contains independent `claude` and `opencode` namespaces. A change under one host must not affect the other host.

### 3.2 Version 2 format

Version 2 retains the current static route fields and adds optional windows:

```json
{
  "version": 2,
  "catalog": {
    "opencode": {
      "provider/default-model": { "variants": ["low", "high"] },
      "provider/window-model": { "variants": ["high"] }
    }
  },
  "claude": {
    "builder": {
      "standard": {
        "model": "claude-model",
        "effort": "high"
      }
    }
  },
  "opencode": {
    "builder": {
      "standard": {
        "model": "provider/default-model",
        "effort": "high",
        "windows": [
          {
            "name": "weekday-peak",
            "days": ["mon", "tue", "wed", "thu", "fri"],
            "utc": "06:00-10:00",
            "model": "provider/window-model",
            "effort": "high"
          }
        ]
      }
    }
  }
}
```

The example is structural only. The repository must not contain the effective user mapping.

### 3.3 Route semantics

- `model` and `effort` on the role/risk entry are the unconditional default.
- `windows` is optional. An entry without windows is a static route.
- Every window contains a complete model and effort binding.
- Claude effort must be one of `low`, `medium`, `high`, `xhigh`, or `max`.
- OpenCode effort is emitted as generated-agent `variant`. It must appear in `catalog.opencode[model].variants` for the exact selected model.
- OpenCode variant declarations are local assertions about the installed model catalog. `config --sync --host opencode` fails closed when a model has no declaration or the configured effort is absent from it.
- All schedule evaluation uses UTC. No local timezone or daylight-saving conversion is performed.
- A window start is inclusive and its end is exclusive.
- `24:00` is legal only as an end. `00:00` is legal as a start. A window ending at midnight is written as `22:00-24:00`.
- Days use `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, and `sun`.
- Window names must be unique within one role/risk route.
- Windows within one role/risk route must not overlap on any configured day.
- Version 3.1 rejects overnight windows. Its error names the two-window workaround, for example `22:00-24:00` plus `00:00-02:00`.
- Missing routes, invalid windows, and ambiguous mappings fail closed before dispatch.

### 3.4 Version 1 compatibility

- Existing version 1 static mappings continue to load unchanged.
- A version 1 static route is normalized internally to a default route with no windows.
- Version 1 may carry the additive top-level OpenCode variant catalog; Airlock 3.0 ignores it while Airlock 3.1 uses it to validate static OpenCode routes.
- Existing version 1 files are not rewritten automatically.
- Airlock 3.1 writes version 1 while every route is static. It emits version 2 only when the local mapping actually contains windows.
- Airlock 3.0 must reject version 2 rather than silently ignoring time windows. Its existing version check already provides this behavior.
- User and project files may use different supported versions; both are normalized before host/role/risk precedence is applied.

## 4. Deterministic Resolution

### 4.1 Inputs and output

The resolver takes only:

```text
host + role + risk + one captured UTC timestamp + effective local mapping
```

It returns:

```text
model + effort + matched route name + exact host agent
```

The orchestrator receives the result and dispatches the exact named agent. It never chooses, ranks, or substitutes a model.

### 4.2 Evaluation

For each CLI command:

1. Capture one timestamp.
2. Load and validate user and project mappings.
3. Resolve the host/role/risk entry.
4. Match the timestamp against the non-overlapping windows.
5. Use the matching window or the default route.
6. Resolve the exact generated agent name.
7. Emit the selected route in both text and JSON output.

Using one timestamp avoids different calls inside the same command straddling a schedule boundary.

Expected brief shape:

```text
TASK T1 | builder | provider/model | high
ROUTE weekday-peak | evaluated 2026-08-21T07:30:00.000Z
AGENT airlock-builder-provider-model-high
```

The actual output may retain the existing separators, but it must include the route name, evaluation time, model, effort, and exact agent.

## 5. Task Route Pinning

### 5.1 Selection point

The route is selected when `airlock next` emits a task for dispatch. `next` writes only local routing state, not plan state.

- Repeating `next` for the same offered task within five minutes returns the same pinned route.
- An offered `todo` pin expires after five minutes. The next `next` or `start` then resolves the current route, preventing a pre-boundary offer from remaining live indefinitely.
- `start` validates and reuses the offered route.
- Calling `start` directly without a prior `next` resolves and pins the route at start time.
- A doing task always resumes on its pin.
- Config changes and schedule-boundary crossings do not change a doing task.
- `done` and `block` release the task pin.
- Parallel tasks have independent pins.

This preserves compatibility with the current 3.0 command shims, which call `next`, then `start`, then dispatch the brief returned by `next`.

### 5.2 Local state

Pin state lives outside the tracked plan, preferably at:

```text
<git-common-dir>/airlock/router-state.json
```

The key must distinguish worktree, plan path, task ID, and host. A pin records only routing metadata:

```json
{
  "model": "provider/model",
  "effort": "high",
  "route": "weekday-peak",
  "selectedAt": "2026-08-21T07:30:00.000Z"
}
```

No credentials, prompts, token data, or provider account state are stored.

State writes must use the same temporary-file-and-rename pattern as plan writes. A stale pin for a task that is not offered or doing is ignored and may be replaced.

The pin deliberately remains local rather than being written into `airlock.plan.json`. A task-row route would expose the user's selected provider/model in a tracked plan and later commits, violating the local-routing boundary. The small local state store is accepted to preserve both route stability and mapping privacy.

### 5.3 Upgrade recovery

A task already doing during a 3.0.1 to 3.1.0 upgrade has no pin. Airlock may reconstruct one from `startedAt` and the current effective mapping, persist it, and label the route as recovered. This is a one-time compatibility path for persisted 3.x plans, not general fallback behavior.

## 6. Host Integration

### 6.1 Shared behavior

Both hosts use the same validated mapping, UTC matcher, route pinning, output fields, and agent naming rules. Host-specific code is limited to agent generation and dispatch instructions.

`config --sync` becomes host-scoped:

```text
airlock config --sync --host claude
airlock config --sync --host opencode
```

It validates the effective local mapping and generates every required agent for that host without changing route assignments.

### 6.2 Claude Code

Claude may remain entirely static in local configuration. For deterministic effort as well as model selection, Airlock generates one local Claude subagent per distinct role/model/effort combination under:

```text
~/.claude/agents/
```

Generated frontmatter contains:

- a deterministic `name`;
- the role description and tool allowlist from the bundled role;
- the configured `model`;
- the configured `effort`.

`airlock next --host claude` emits the exact generated agent name, and the Claude command shim dispatches that agent rather than asking the orchestrator to infer a role/model combination.

The Claude shim passes no call-time `model` argument. The generated agent's frontmatter is the only Airlock-controlled source of both model and effort.

Airlock must fail closed when `CLAUDE_CODE_SUBAGENT_MODEL` is set because that environment variable overrides the configured subagent model. Documentation must also note that organization model restrictions can substitute a model and organization effort limits can clamp effort. Full model IDs are required when exact version pinning matters; aliases such as `sonnet` and `opus` intentionally follow Claude's alias resolution.

`config --sync` and `next` must also fail closed when a project-level `.claude/agents/<generated-name>.md` shadows the user-level generated agent.

### 6.3 OpenCode

OpenCode may use the more complex scheduled mapping. Airlock generates one local OpenCode subagent per distinct role/model/effort combination under:

```text
~/.config/opencode/agents/
```

Synchronization must include every default route and every scheduled window route. `next --host opencode` emits the exact generated agent name already required by Airlock 3.0. The legacy singular `~/.config/opencode/agent/` directory is detected and reported during migration but is not used for newly generated 3.1 agents.

OpenCode's agent-file and `variant` behavior is verified against the current v1 configuration surface as of 2026-08-21. OpenCode's v2 configuration work remains a moving external dependency and is not adopted speculatively in Airlock 3.1.

OpenCode must be restarted after first creating its agent directory or after synchronization when the running process has not loaded the new candidates.

### 6.4 Generated-file policy

- Agent names remain deterministic from role, model, and effort.
- Identical role/model/effort combinations are generated once even when several risks or windows reference them.
- Synchronization does not delete stale agents automatically.
- Synchronization reports created, existing, missing, and stale Airlock-generated agents.
- `next` refuses before offering a task when its selected agent is missing and prints the exact host-scoped sync command. `start` repeats the check as a second gate.
- `config --sync --prune` removes only stale Airlock-generated agents that no effective route or active pin references.

## 7. CLI Changes

### 7.1 `config`

The existing command remains valid for static routes:

```text
airlock config --host <host> --role <role> --risk <risk> --model <model> --effort <effort>
```

For a version 2 file it updates the default model and effort without silently changing windows. Scheduled mappings may be authored directly in the local JSON file in 3.1.

Add:

```text
airlock config --sync --host <claude|opencode>
airlock config --sync --prune --host <claude|opencode>
```

Sync output includes the effective config paths, generated agent paths, declared OpenCode variants, and stale paths so duplicate platform config locations are visible.

### 7.2 `next`, `status`, and `render`

- `next` resolves or reuses the pin and prints the exact route.
- `status` uses pins for doing tasks and an unexpired offered pin for the next todo task; otherwise it shows a current-time preview. It must not create a pin.
- `render` follows the same read-only route behavior as `status`.
- Human-readable output labels routes as `PINNED`, `PREVIEW`, or `RECOVERED`; this distinction is not JSON-only.
- JSON output includes `model`, `effort`, `route`, `evaluatedAt`, `agent`, and whether the route is pinned or previewed.

### 7.3 Lifecycle commands

- `start` reuses an offered pin or creates one if invoked directly.
- `done` clears the pin after successful task completion.
- `block` clears the pin after preserving blocked work.
- Reopened tasks have no old pin and resolve again on their next dispatch.

No new top-level routing command family is added in 3.1.

## 8. Implementation Work

### 8.1 Specification

Use this document as the implementation source. Do not retain the earlier weighted/quota routing proposal.

### 8.2 CLI core

Update `scripts/airlock.mjs` to:

1. Parse and validate local mapping versions 1 and 2.
2. Normalize both versions into one internal route shape.
3. Merge user and project routes by complete host/role/risk entry.
4. Parse and validate UTC windows.
5. Reject overlapping windows.
6. Resolve a route against an injected timestamp.
7. Read, write, and clean local task pins.
8. Resolve routes once per command.
9. Generate host-specific agents from every candidate route.
10. Validate Claude effort and per-model OpenCode variants before generation.
11. Support host-scoped `config --sync` and safe `--prune`.
12. Refuse missing or shadowed agents at `next` and `start`.
13. Add route metadata to text and JSON output.

Keep the implementation dependency-free and in the current CLI module unless a helper becomes independently testable and materially reduces complexity.

### 8.3 Host shims

Update:

- `commands/airlock.md`
- `.opencode/command/airlock.md`

Both shims must dispatch the exact `AGENT` emitted by `next`. They must not calculate time, select a model, or interpret effort. The Claude shim must not pass a call-time `model` parameter. Preserve the existing run loop and lifecycle order.

### 8.4 Documentation and metadata

Update:

- `README.md`
- `package.json`
- `.claude-plugin/plugin.json`
- `.claude-plugin/marketplace.json`

Set the release version to `3.1.0` and update tagged installation examples. Do not create a tag, publish a package, push, or release without a separate explicit request.

## 10. Local Rollout After Release

Local rollout is separate from repository implementation and must not be encoded in repository defaults:

1. Install or link Airlock 3.1 locally.
2. Back up the effective local mapping.
3. Convert only the effective local file to version 2.
4. Keep Claude routes static unless a Claude schedule is explicitly wanted.
5. Add the desired OpenCode default and window routes using direct provider model IDs.
6. Run `airlock config --sync --host claude`.
7. Run `airlock config --sync --host opencode`.
8. Restart hosts when required to load newly generated agents.
9. Verify one static Claude route and both sides of an OpenCode time window.
10. Run a small plan and confirm route, model, effort, and exact agent output.
11. Leave historical LiteLLM aliases available but unreferenced during migration.
12. Stop LiteLLM by default only after direct routes pass.
13. Run host-scoped `config --sync --prune` after reviewing the exact stale-agent list; active routes and pins remain protected.

## 11. Acceptance Criteria

Airlock 3.1 is complete when:

1. The same host, role, risk, timestamp, and local mapping always select the same route.
2. The orchestrator cannot choose or substitute an Airlock route.
3. Claude and OpenCode mappings are independent.
4. Claude can use simple static mappings with deterministic model and effort agents.
5. OpenCode can use deterministic UTC windows.
6. A new task changes routes exactly at configured UTC boundaries.
7. A doing task never changes routes because the clock or config changed; an offered task is stable for the five-minute dispatch window.
8. Version 1 static mappings continue to work.
9. Version 2 scheduled mappings fail closed under Airlock 3.0.
10. Every selected host agent exists before dispatch.
11. Claude effort and each OpenCode model variant are validated before dispatch.
12. The Claude shim supplies the exact agent and no call-time model override.
13. No real user model assignment is committed to this repository.
14. No quota, weighted-routing, provider-probing, or request-level fallback code is added.
15. The full existing and new test suite passes on the supported Windows development host.
