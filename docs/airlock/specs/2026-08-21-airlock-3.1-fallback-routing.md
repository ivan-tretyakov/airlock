# Airlock 3.1 Ordered Fallback Routing Amendment

**Status:** implementation source
**Date:** 2026-08-21
**Baseline:** Airlock 3.1.0

## Goal

Add deterministic ordered fallback candidates to Airlock's existing per-task model, effort, and UTC-window routing. This replaces LiteLLM failover for Airlock workers without adding retries, weighted routing, health probing, cooldowns, or quota tracking.

## Configuration

Fallbacks require local mapping version 3. A default route and each window are complete bindings with their own ordered `fallbacks` array of at most two candidates. Fallback candidates contain `model` and `effort`. Duplicate candidates, empty arrays, oversized chains, unsupported effort or variant names, and fallback fields on older mapping versions fail closed.

Version 1 static routes and version 2 scheduled routes remain valid. Older binaries reject version 3 instead of ignoring fallback behavior. Project role/risk entries continue to replace complete user entries.

## Resolution And Pinning

Airlock captures one UTC timestamp and selects either the matching window or the default binding. It pins the complete ordered chain, active candidate index, route name, and evaluation time. Offered pins keep the existing five-minute expiry. Doing tasks keep the same chain across configuration and schedule changes.

Router state version 2 stores candidate chains and bounded failure metadata. Version 1 pins load as one-candidate chains and upgrade on the next state write. Agent synchronization generates every candidate and pruning protects every candidate referenced by an active pin. On successful completion, the active pin moves to a local `completed` map keyed by task id, commit SHA, and host; this preserves the executing candidate and failure history without exposing model assignments in the tracked plan or commit.

## Dispatch Failure

`airlock fallback <task-id> --host <host> --class <class> --reason "<cause>"` advances a doing task by exactly one candidate and emits a fresh TASK block with the exact generated agent. Class is a closed declaration: `auth`, `rate-limit`, `timeout`, `transport`, or `model-unavailable`. It is stored with the failure record. The command fails when no candidate remains, two advances have already occurred, or the next agent is missing or shadowed.

Host shims may invoke fallback only when the dispatch tool itself errors before returning any child result. They must map that error to the closed class set. Cancellation, permission errors, configuration errors, and child-returned failures do not trigger fallback. The class makes the orchestrator's assertion auditable; it cannot independently prove host behavior.

Before advancing, Airlock audits the worktree. Any task-owned or unattributed out-of-scope change means the child may have started work, so fallback is refused. Changes owned by a separate concurrently-doing task remain foreign and do not block the current lane.

## Output

Text output names the active `AGENT` and remaining `FALLBACK` agents. JSON output includes `candidateIndex`, the complete candidate list, and prior classified failure metadata. `status` shows the active candidate position for a doing task. Completed local records retain the same route metadata plus task id, commit SHA, host, worktree, plan path, and completion time.

## Acceptance

1. The same host, role, risk, timestamp, and mapping produce the same ordered chain.
2. UTC windows select complete chains and do not inherit fallback candidates.
3. Each fallback attempt advances once and remains pinned.
4. No fallback occurs after a child result or a detected worktree change.
5. All candidate efforts and OpenCode variants are validated before generation.
6. Every candidate agent exists before initial dispatch.
7. Active pins protect the complete chain from pruning.
8. Version 1 and 2 mappings and version 1 router pins remain compatible.
9. Every fallback records a valid class and no task advances more than twice.
10. Successful completion retains the executing route locally by task and commit.
