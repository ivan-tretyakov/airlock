# Airlock 4.0 — Slim Core

- Date: 2026-09-01
- Status: draft (revised same day to resolve `../reviews/2026-09-01-airlock-4.0-review.md`, F1–F16)
- Supersedes: 3.1 routing (`../archive/2026-08/2026-08-21-airlock-3.1-routing.md`, `../archive/2026-08/2026-08-21-airlock-3.1-fallback-routing.md`) for the removed subsystems

## Motivation

A comparative assessment against the mid-2026 ecosystem (native Claude Code plan mode, task lists, background subagents, native model fallbacks; Wayfinder; Superpowers; Spec Kit) concluded:

1. Airlock's differentiated, defensible value is the **deterministic execution core**: a validated plan artifact, ownership-scoped git audit, per-task commits with evidence, and the assume/answer decision buffer. No popular alternative has this.
2. The **routing subsystem** (role×risk routes, UTC windows, 5-minute pins, ordered fallback chains, OpenCode variant catalogs, generated per-route agents) is the largest share of the CLI, has already forced two breaking migrations, and duplicates capability hosts now provide natively (model selection per agent, host-level fallback across models). Its cost/benefit no longer holds.
3. Maintenance economics for a bus-factor-one tool demand the smallest possible host-facing surface.

4.0 removes routing wholesale, collapses the risk taxonomy, drops legacy import, and rewrites the README around real workflows. It keeps everything that makes Airlock worth using.

## Decision summary

| Subsystem | 3.1 | 4.0 |
|---|---|---|
| Plan schema, ownership, acceptance, dependencies | keep | keep (v4) |
| Ownership audit, `--revert-out-of-scope`, preservation refs | keep | keep unchanged |
| Per-task commit with `Airlock-Task` trailer + evidence | keep | keep unchanged |
| Decisions: `ask --assume` / `--blocking`, `answer`, rework reopening | keep | keep unchanged |
| `--parallel` disjoint-ownership dispatch | keep | keep unchanged |
| Model routing (routes, windows, pins, catalogs, `config`, `fallback`) | core | **removed** |
| Generated per-route host agents (`config --sync`) | core | **removed** — three static role agents |
| Risk taxonomy `light|standard|complex|critical` | core | **replaced** by optional boolean `expensive` |
| `import` (2.x ledger) | utility | **removed** |
| Herdr extension | optional | **frozen at 3.x** (requires the 3.x release precondition in §Versioning) |

## Plan schema v4

`schema` becomes `"airlock.plan/v4"`.

Task changes:

- `risk` is removed. An optional boolean `expensive` replaces it. Semantics: absent means not expensive; an explicit `expensive: false` is **accepted** and equivalent to absent (hand-authors and JSON generators that always emit the field must not trip on it); any non-boolean value is rejected with `task <id> expensive must be a boolean`. `budget.maxExpensive` counts tasks with `expensive: true`. Everything else about budget enforcement (`selectNext`, `budgetState`, `isExpensive`) is preserved: `isExpensive(task)` returns `task.expensive === true`.
- A residual `risk` field on a v4 task is **rejected**, fail closed — `validatePlan` (which otherwise ignores unknown fields) checks for it explicitly: `task <id> risk was removed in v4; use expensive: true for critical-cost tasks`. This protects an author who hand-migrates by rewriting `schema` but keeps `risk: "critical"`, which would otherwise silently lose budget protection.
- `model` on a task remains rejected; the message becomes `task <id> model is not supported; model choice belongs to the host agent files`.
- All other task fields (`id`, `title`, `role`, `owns`, `dependsOn`, `acceptance`, `status`, `evidence`, `note`, `startedAt`, `finishedAt`) and all decision fields are unchanged.

### v3 read compatibility

`readPlan` accepts `airlock.plan/v3` and upgrades it in memory before validation:

- `risk: "critical"` → `expensive: true`; `light|standard|complex` → field absent. This is faithful to 3.x budget semantics, where `isExpensive` counted only `critical`.
- `schema` → `airlock.plan/v4`.
- A v3 task that already carries an `expensive` field (invalid for v3, but pre-upgrade content is unvalidated) is rejected by the upgrade function, fail closed: `task <id> has both risk and expensive; a v3 plan must not carry expensive`.
- v2 and earlier and unknown schemas remain rejected (the 2.x `import` path is removed; users on 2.x must go through a 3.x release first, documented in Migration).

`validatePlan` validates v4 only. The upgrade is a pure function with its own tests.

**UPGRADED notice.** When `readPlan` performs the upgrade, the CLI emits a notice that must never corrupt the stdout contract (one payload per invocation: plain text, or one JSON document in `--json` mode):

- The notice line is written to **stderr** in all modes: `UPGRADED plan schema airlock.plan/v3 -> airlock.plan/v4`, with the suffix ` (risk: critical -> expensive on <ids>)` appended **only** when at least one task actually mapped (F14: no constant parenthetical when nothing was critical).
- In `--json` mode the JSON document additionally carries an `upgraded: true` top-level field so machine consumers see the fact without parsing stderr. stdout stays a single valid JSON document.
- stdout's first line remains `TASK …`/`NOTHING TO DO`/`STARTED …`/the JSON document — the notice never precedes or follows it on stdout, so first-line shim dispatch is unaffected.
- The notice is emitted at most once per invocation, including error paths: it is written when the upgrade happens (at `readPlan` time), so `next --unattended` on a v3 plan prints the stderr notice and then the `PARKED` error (exit 2), and a post-upgrade validation error is likewise preceded by the notice on stderr.

**Persistence.** Any command that mutates plan state persists the upgraded (v4) form: `start` — including its resume branch, which today returns without writing and in 4.0 calls `writePlan` when `readPlan` upgraded the plan — `done`, `block`, `ask`, and `answer`. Read-only commands (`next`, `status`, `audit`, `render`) do **not** rewrite the file; they emit the stderr notice on every invocation instead. Consequence, stated deliberately: a plan that is only ever read stays v3 on disk indefinitely and the notice repeats each run — acceptable, because the first state mutation converts it and read-only use is harmless.

## Routing removal

Delete outright, with their tests:

- Commands: `config` (both forms), `fallback`, `import`.
- Constants: `RISKS`, `CLAUDE_EFFORTS`, `FALLBACK_CLASSES`, `MAX_FALLBACK_ADVANCES`, `OFFER_PIN_TTL_MS`.
- Route configuration: `userConfigDir/userConfigPath/projectConfigPath`, `readRoutes`, `loadRoutes`, `mergeRoutes`, `routeEntries`, `routesForWrite`, `effectiveRoutesAfterUpdate`, `configureRoute`, `routeGuidance`, `validateCandidate/validateFallbacks/validateWindow/validateRoute`, `parseClock`, `dayName`, `resolveConfiguredRoute`, `openCodeVariantError`.
- Router state: `routerStatePath`, `readRouterState/writeRouterState`, `normalizePin`, `pinKey`, `routeFor`, `ensureRoutePin/clearRoutePins/completeRoutePin/activateRoutePin/clearInactiveRoutePins`, `advanceRouteFallback`.
- Generated agents: `agentName`, `routeAgentPath`, `assertRouteAgent`, `assertSelectedAgent`, `routeCandidates`, `desiredHostAgents`, `syncHostAgents`, `agentMarkdown`, `roleTools` (only `agentMarkdown` consumed it; the Claude agents are now the `roles/` files themselves and the OpenCode generation needs only `roleBody`), and the `CLAUDE_CODE_SUBAGENT_MODEL` guard.
- Host directories and their env overrides: `openCodeConfigDir` (with `OPENCODE_CONFIG_DIR` handling — the 4.0 OpenCode bootstrap writes only into the project's `.opencode/`, never the user config dir) and `claudeAgentsDir` (with `AIRLOCK_CLAUDE_AGENT_DIR`).
- Other newly dead code: `configText` (only the removed `config` branch called it), `importLedger` (only the removed `import` branch called it), and the now-unused `unlinkSync` and `readdir` imports.
- Output plumbing: `routeState`, `routeOutput`, `dispatchLines` (replaced by a static `AGENT` line), the `ROUTE`/`FALLBACK` lines in `taskText`/`start` output, the route/model fragments in `statusText` rows and `renderMarkdown` (exact 4.0 shapes in §Output shapes), the `routes` array in `status --json`, and the `CLOCK OVERRIDE` marker and `clockOverride` flag.

`AIRLOCK_NOW` is retained solely as a deterministic timestamp source for tests (`commandNow` keeps honoring it); with no time-dependent behavior left, no override marker is printed.

Existing local artifacts (`models.json` user and project copies, `router-state.json`, generated `airlock-<role>-<model>-<effort>` agents in `~/.claude/agents/` and the OpenCode user config dir) are **ignored, never deleted**. Migration documents how a user may remove them by hand.

## Dispatch model

`next`/`start` emit `AGENT airlock-<role>` — a static name per role, no model, no effort. `roles/` stays and remains the **single source** of role bodies and tool lists for both hosts; the 3.x generated agents (`airlock-<role>-<model>-<effort>` files) disappear and nothing regenerates them.

- **Claude Code**: `.claude-plugin/plugin.json` **already** registers `"agents": ["./roles/builder.md", "./roles/checker.md", "./roles/browser.md"]`; these entries and paths are kept as-is. The only change to the role files is the frontmatter rename `name: builder|checker|browser` → `name: airlock-builder|airlock-checker|airlock-browser`, so the plugin-bundled agent names match the `AGENT` line exactly (today no agent named `airlock-builder` exists anywhere — the generated ones carried model/effort suffixes). Frontmatter stays `name`, `description`, `tools`; **no `model`, no `effort`** — the agent inherits the session's model. Acceptance step before release: install the plugin and confirm a subagent dispatch to the literal string `airlock-builder` resolves; if the host resolves plugin agents only under a namespaced identifier (e.g. `airlock:airlock-builder`), adjust the `AGENT` line format to the resolvable form and record it here.
- **OpenCode**: `init --host opencode` bootstraps `.opencode/agent/airlock-builder.md`, `airlock-checker.md`, `airlock-browser.md` alongside the command shim it already writes. Their content is **generated from `roles/`** at init time, exactly as 3.x `agentMarkdown` did minus model/variant: frontmatter is the role's `description`, `mode: subagent`, and `permission:\n  edit: deny` for checker and browser (no `model`, no `variant`, no `tools:` line — OpenCode uses `permission`); the body is `roleBody(role)` (`roleSource`/`roleBody` are kept unchanged, still reading `../roles/<role>.md`; `roles` is already in `package.json` `files`, so the npm-installed CLI can read it). Re-running init refreshes unmodified files and refuses to overwrite customized ones (same content-hash guard strategy as the command shim).
- **Model customization**: Airlock no longer mediates model choice; host-native fallback handles model failures. On OpenCode, the user edits the project-local `.opencode/agent/airlock-<role>.md` (hash-guarded, so init preserves the edit). On Claude Code the bundled files live inside the installed plugin and are overwritten on plugin update, so editing them is **not** the channel: the user creates a same-named override — project `.claude/agents/airlock-<role>.md` or user `~/.claude/agents/airlock-<role>.md` — with the same `name:` and a `model:` line, which the host resolves in preference to the plugin copy. The 3.x shadow guard (`assertRouteAgent`'s "project agent shadows local Airlock route" error) is removed **deliberately**: shadowing flips from a routing-integrity violation to the intended customization mechanism. Acceptance step before release: verify the host's actual precedence order (project over user over plugin) and record it in the README Hosts section.

## Output shapes

`taskText` shape (unchanged fields omitted):

```
TASK <id> · <role>
GOAL  ...
DO    ...
OWNS  ...
DONE  <acceptance>
AGENT airlock-<role>
ASSUME ...            (when applicable)
EVIDENCE/DIFF ...     (checker dependency context, unchanged)
RULES ...             (unchanged)
```

- `start` prints `STARTED <id>` (fresh) or `STARTED <id> (resume)` followed by `AGENT airlock-<role>`; the `ROUTE` line is deleted. The resume branch is exactly the v3-migration path (a mid-`doing` task whose 3.x pin vanished with router state), so it must work with no router artifacts present.
- `statusText` DOING rows become `  <id>  <title>  <role>  <duration>` (route model, `routeState`, and candidate counts are gone); NEXT rows become `  <id>  <title>  <role>`. GOAL/NEEDS YOU/ASSUMED/BLOCKED/BUDGET sections are unchanged.
- `render --md`: the task table's `Route` column is replaced by the role — header `| ID | Task | State | Role |`, rows `| <id> | <title> | <status> | <role> |` (the agent name is derivable as `airlock-<role>` and adds nothing).
- JSON shapes: `next` returns `{text, task, agent}` (`route` object deleted; `agent` is the static `airlock-<role>` or `null` when nothing was selected); `start` returns `{text, task, agent}`; `status` returns `{text, plan}` — the `routes` array is deleted outright with no replacement (it existed only to expose pins; static agents are derivable from `plan`). All of these carry `upgraded: true` when §v3 read compatibility applies.

## Command surface

Coordinator verbs: `next`, `start`, `done`, `block`, `ask`, `answer`, `status`, `audit`. Utilities: `init`, `render`. (`config`, `fallback`, `import` removed; `help` updated.)

- `--host claude|opencode` is **meaningful only** on `init` (it selects OpenCode bootstrap). On every other command the flag is **accepted and ignored** as a deprecated no-op — both 3.x shims pass `--host` to every verb, and the OpenCode hash guard deliberately preserves customized shims, which keep passing it until their owner re-runs `init` and merges; rejecting it would break every preserved shim with an unrelated-looking error. `parseCli` collects flags generically, so acceptance is zero-cost. The `AIRLOCK_HOST` env variable is likewise no longer read anywhere (deprecated no-op; setting it has no effect). Help text documents `--host` under `init` only.
- `--plan`, `--json`, `--unattended`, `--parallel`, `--range`, `--revert-out-of-scope` behave as in 3.1.
- `start` on a dispatch that later fails has one recovery path: the shim runs `block <id> --reason "<cause>"` (fallback classification is gone). `block` semantics, including preservation of a doing task's changes under `refs/airlock/blocked/...`, are unchanged.

## Host shims

Both shims are rewritten without the fallback-classification branch and without `--host` on the coordinator verbs. Claude (`commands/airlock.md`), same loop otherwise: `next` → dispatch TASK to its `AGENT` → on dispatch error `block` with the cause → after a child result `audit` → `done --evidence` → repeat; `PARKED` and `NOTHING TO DO` handling unchanged. The OpenCode shim mirrors it and its install line moves to `#v4.0.0` (see §Versioning). The tested 5,000-byte prompt-surface ceiling stays with its current composition — it already sums `commands/` + `roles/` + `.opencode/command/` — and the 800-byte per-role ceiling stays (the `name:` rename adds ~8 bytes per role file, well inside it).

OpenCode shim upgrade: `LEGACY_OPENCODE_COMMAND_HASHES` currently holds only the two 3.0-era hashes; **add** the hash of the packaged 3.1 shim (`9201872f0c11c80d2a76b90bd14afc911943f7cf2923bd4212798a07eaba6e8e`, computed with the CLI's `\r\n` normalization) so an unmodified 3.1 shim auto-upgrades instead of hitting the manual-merge error. A customized shim still fails with the manual-merge instruction. The `--class <class>` marker probe is replaced by a probe for the 4.0 shim's distinguishing content (e.g. its `AGENT airlock-` dispatch sentence).

## Extensions

The Herdr adapter targets the 3.x CLI surface (routes, `fallback`, generated agents) and is **frozen at 3.x**. Current reality, verified: `extensions/` is uncommitted (untracked; no commit anywhere contains it) and no `v3.1.x` tag exists — the only tags are `v3.0.0` and `v3.0.1`, so the README's `#v3.1.0` install line is already dangling. The freeze is therefore a **release precondition**, not a description of the status quo: before 4.0 lands, commit `extensions/herdr` on the 3.x line and cut a `v3.1.x` tag containing it (this also repairs the dangling install instruction). See §Versioning. This spec touches no files under `extensions/` — the README gains one line stating the adapter requires Airlock 3.x. Porting it to 4.0 would be its own spec.

## README and template rewrite

Sections removed: model routing configuration, `config --sync`, fallback chains, OpenCode catalogs, migration from 3.0.x, importing from 2.x. Sections updated: Quick Start, Plan File (v4, `expensive`), Commands, Hosts (static agents, the Claude override-agent customization path from §Dispatch model), Validation.

New **Workflows** section with four worked examples:

1. **Below the threshold** — one task with one obvious verification command: no plan, just do the work. Airlock's own guidance stays: use it only when delivery spans multiple tasks with distinct ownership.
2. **Well-understood multi-task feature** — resolve open design questions first (an interrogation skill such as Matt Pocock's `/grill-me` works well), then `airlock init` with testable `--done` criteria, author tasks whose `acceptance` lines come from the resolved questions, run `/airlock`. Includes a complete example plan JSON (export-feature shaped: two builders + one consolidated checker with `dependsOn`).
3. **Ambiguous multi-week work** — keep a decision map upstream (e.g. Wayfinder or a markdown decision log), convert each fog-free region into one Airlock plan, execute, note the resulting `Airlock-Task` commits back on the map. Airlock deliberately owns only the execution slice.
4. **Intake routing** — bugs and questions are not plan items: file bugs in the issue tracker with the repro command (that text later becomes an `acceptance` line); codebase questions are just conversation; questions that arise mid-run are `airlock ask --assume` (or `--blocking` for the five allowed cases); design unknowns before any plan exists belong in the upstream decision map, not in `airlock.plan.json`.

The Authoring-tasks guidance is rewritten for `expensive` (drop the four-level risk prose; keep the consolidated-checker-near-the-end guidance and the builder-run-acceptance guidance verbatim in spirit).

**`PROJECT-CONVENTIONS.template.md`** is a packaged, user-facing template and is rewritten in the same pass — today it teaches the four-level risk taxonomy and local routing, both of which produce invalid plans under v4:

- The risk bullet ("Default to `standard` … Reserve `critical` …") is replaced by `expensive` guidance: mark a task `expensive: true` only for irreversible, security-sensitive, or migration work; `budget.maxExpensive` caps it deliberately.
- The "Keep model routing in the local Airlock configuration" bullet is deleted (there is no routing; per-role model preferences live in host agent files per §Dispatch model).
- The builder-run-acceptance and consolidated-checker bullets are kept, reworded only to drop the risk-level references ("Builder-run acceptance is sufficient for tasks whose acceptance one command captures"; per-task checkers reserved for `expensive` tasks).

## Tests

Remove: window/schedule tests, fallback-chain and pin tests, catalog/variant tests, `config` tests, `import` tests, route-binding consistency tests.

Keep and adapt: schema invariants (now v4), lifecycle transitions, assumption rework, Git audits including shell-created writes, overlap/parallel serialization, budget caps (via `expensive`), prompt-surface ceiling.

Add:

- v3 → v4 upgrade mapping (each risk level; a v3 task already carrying `expensive` is rejected).
- `UPGRADED` notice contract: emitted on stderr, not stdout; stdout first line stays `TASK`/`NOTHING TO DO`; in `--json` mode stdout is one valid JSON document with `upgraded: true`; notice includes the `(risk: critical -> expensive on <ids>)` suffix only when a critical task existed; notice precedes the `PARKED` error on a v3 plan under `--unattended`.
- Persistence: after any state-mutating command the plan file is v4; after read-only commands (`next`, `status`) a v3 plan remains v3 on disk and the notice re-appears.
- v3 resume path: a mid-`doing` v3 plan → `start <id>` prints `STARTED <id> (resume)` + `AGENT airlock-<role>` and persists the plan as v4.
- v2/v1 plans and unknown schemas still fail closed.
- `expensive` validation: explicit `false` accepted and not counted; non-boolean rejected; `true` counted against `maxExpensive`; a v4 task carrying `risk` rejected with the pointer message.
- Static `AGENT airlock-<role>` line in `next`/`start` output; absence of `ROUTE`/`FALLBACK` lines; `status --json` has no `routes` key; `render --md` header is `| ID | Task | State | Role |`.
- `task.model` rejection message.
- `--host` accepted and ignored on non-`init` commands (a preserved 3.x shim invocation like `next --host opencode` succeeds).
- `init --host opencode` writes three agent files generated from `roles/`; the packaged 3.1 shim content (real bytes, not a fixture) auto-upgrades; a customized shim fails with the manual-merge error.
- Prompt-surface test updates: the 5,000-byte sum and 800-byte per-role ceilings stay as-is; the shim marker assertions flip — keep `match /unattended/`, drop the matches for `fallback <id>`, `--class <class>`, and `Never fallback after any child result` and assert their **absence**; drop the per-verb `--host claude|opencode` matches and assert the shims pass no `--host`; the install-line assertions move from `#v3.1.0`/`#v3.0.0` to `#v4.0.0` (the historical-tag sentence is dropped from the 4.0 shim: a 3.x global install cannot drive a v4 plan, so advertising old tags in the 4.0 shim would misdirect recovery).

## Versioning and migration

- **Precondition (Herdr freeze):** commit `extensions/herdr` on the 3.x line and tag a `v3.1.x` release containing it before 4.0 lands (repairs the currently dangling `#v3.1.0` README install tag; today only `v3.0.0` and `v3.0.1` exist).
- Version bump moves **all** version-bearing surfaces together (per the 3.2 review convention): `package.json` → `4.0.0`; `.claude-plugin/plugin.json` → `4.0.0`; `.claude-plugin/marketplace.json` plugin entry → `4.0.0`; README global-install line → `#v4.0.0`; the rewritten OpenCode shim's own install line → `#v4.0.0`; the test assertions that pin these strings (see §Tests).
- Migration notes (README): plans upgrade automatically on the first state-mutating command (read-only use emits a stderr notice and leaves the file at v3); local `models.json` (user and project), `router-state.json`, and generated `airlock-<role>-<model>-<effort>` agents are obsolete and may be deleted by hand; per-role model preferences move into host agent files (OpenCode: edit `.opencode/agent/airlock-<role>.md`; Claude: create an override agent per §Dispatch model); the Herdr adapter requires 3.x (`v3.1.x` tag).
- 2.x users: import path removed — run a 3.x release once, or author the v3/v4 plan by hand.

## Out of scope

- No new commands or verbs. No backlog, issue-tracker, or upstream-planning features in the CLI (docs-only guidance).
- No Herdr port.
- No behavior change to audit, commit, decision, or parallel-dispatch semantics.
