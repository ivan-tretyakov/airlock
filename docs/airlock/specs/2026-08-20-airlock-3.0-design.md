# Airlock 3.0 — Design Specification

**Status:** approved design input (user-commissioned, 2026-08-20). Implementing session runs planning from this document; no separate brainstorm needed.
**Baseline:** 2.5 merged (`00d6200`); 2.6 unmerged and superseded by this design.
**Breaking:** yes. Artifacts, commands, and agent roles all change. Hence 3.0.

## 1. Objective

**Primary:** agent orchestration with a clearly defined goal and contract/plan, working **natively on Claude Code and OpenCode**, with **multimodel slim roles**.

**Secondary:** token efficient · concise, actionable user instructions · no overdocumentation that later goes obsolete · faster delivery.

**Explicitly demoted:** runtime safeguards. They matter, but they are not why Airlock exists, and four of the last five releases were spent on them.

### The two constraints that decide the architecture

1. **"Natively on both hosts" forbids host-specific enforcement in the core.** The portable substrate is exactly: filesystem, git, shell command execution, subagent dispatch, per-dispatch model selection, markdown prompt files. Hooks are not in that set. Anything built on hooks is an adapter, and adapters are what broke 2.6 (`apply_patch`), 2.4 (`actorMode`), and 2.2 (contract root under OneDrive).
2. **The contract's real job is briefing, not fencing.** Its value is that a fresh worker knows exactly which files to touch and what "done" means — which is what saves tokens and rework. Enforcement was a bonus that became the tail wagging the dog.

**Governing principle: validate the plan, not the tool call.** Refuse a task with no acceptance criteria and no owned paths, at plan time, while the user is present. Do not block tool calls at 02:00.

## 2. Architecture

```
airlock.plan.json          ← the single authored artifact (goal, tasks, decisions, state)
     ↑ read/write
airlock (CLI, Node, no deps)  ← the coordinator: next / start / done / block / ask / status / audit
     ↑ invoked by
one host shim per harness  ← ~20 lines of markdown, contains no policy
     ↓ dispatches
3 roles × N model bindings ← builder / checker / browser
```

Everything the model sees is CLI output. The model never reads the plan file.

## 3. State file — `airlock.plan.json`

One per delivery, at repo root or `docs/airlock/`. Replaces plan, ledger, STATUS, and DECISIONS entirely.

```json
{
  "schema": "airlock.plan/v3",
  "goal": "Promo price table supports by-product rows",
  "done": ["yarn test passes", "by-product view renders product×retailer rows keyed on referenceId"],
  "nonGoals": ["no change to the scenario list page"],
  "created": "2026-08-20T09:00:00Z",
  "budget": { "maxTasks": 8, "maxExpensive": 2 },
  "tasks": [
    {
      "id": "T1",
      "title": "Add referenceId keying to grouping util",
      "role": "builder",
      "risk": "standard",
      "model": "sonnet",
      "owns": ["src/_lib/utils/grouping.ts", "src/_lib/utils/grouping.test.ts"],
      "dependsOn": [],
      "acceptance": "yarn test src/_lib/utils/grouping.test.ts passes with a new case for duplicate names",
      "status": "todo",
      "evidence": [],
      "startedAt": null,
      "finishedAt": null,
      "note": null
    }
  ],
  "decisions": [
    {
      "id": "D1",
      "question": "Read-only or editable Value column on shared offers?",
      "options": ["read-only", "editable with confirm"],
      "recommendation": "read-only",
      "mode": "assume",
      "assumed": "read-only",
      "blocks": ["T4"],
      "consumedBy": [],
      "status": "open",
      "answer": null,
      "askedAt": "2026-08-20T11:00:00Z"
    }
  ]
}
```

**Field rules.**

| Field | Rule |
|---|---|
| `goal` | One sentence. Required. |
| `done` | ≥1 testable criterion. Required. `init` refuses without it. |
| `tasks[].owns` | ≥1 path or glob. Required. This is the contract. |
| `tasks[].acceptance` | One testable statement. Required. `next` refuses to emit a task without it. |
| `tasks[].role` | `builder` \| `checker` \| `browser` |
| `tasks[].risk` | `light` \| `standard` \| `complex` \| `critical` |
| `tasks[].model` | Optional explicit override; otherwise resolved from `risk` via project config |
| `tasks[].status` | `todo` \| `doing` \| `blocked` \| `needs-you` \| `done` |
| `decisions[].status` | `open` \| `answered` |
| `decisions[].mode` | `assume` (default) \| `block`. `assume` requires a non-null `assumed`. See §4.1 |
| `decisions[].consumedBy` | task ids that were executed against the assumption; drives rework if the user answers differently |

**Invariants** (checked by every write command; violation exits non-zero with the exact reason):

- ids unique; `dependsOn` references exist; no cycles
- at most one task in `doing` unless `--parallel` and the `owns` sets are disjoint
- a `done` task has ≥1 `evidence` entry
- a `blocked` task has a `note`
- a task blocked by an open **`block`-mode** decision cannot be `doing`
- a task blocked by an open **`assume`-mode** decision may run; the run appends its id to that decision's `consumedBy`

**Model resolution** — project config `.airlock/models.json`, per harness:

```json
{
  "claude":   { "light": "haiku", "standard": "sonnet", "complex": "sonnet", "critical": "opus" },
  "opencode": { "light": "zai-coding-plan/glm-5.3", "standard": "zai-coding-plan/glm-5.3",
                "complex": "zai-coding-plan/glm-5.3", "critical": "openai/gpt-5.6-sol" }
}
```

Risk → model is data, not prompt text. Changing the cost profile is a config edit, not a release. `complex` deliberately does **not** default to the most expensive tier (carried from 2.5).

## 4. CLI — `airlock`

Dependency-free Node, `scripts/airlock.mjs`, exposed as `node scripts/airlock.mjs <cmd>` or an `airlock` bin. Identical behaviour on both hosts. All output is plain text sized for a prompt; `--json` on every command for tooling.

### `airlock init "<goal>"`
Creates the skeleton, prompts for `done` criteria, exits non-zero if none supplied. Never overwrites an existing plan.

### `airlock next`
The coordination heart. Selects the first task with `status: todo`, all `dependsOn` done, and no open blocking decision. Prints exactly:

```
TASK T1 · builder · sonnet
GOAL  Promo price table supports by-product rows
DO    Add referenceId keying to grouping util
OWNS  src/_lib/utils/grouping.ts
      src/_lib/utils/grouping.test.ts
DONE  yarn test src/_lib/utils/grouping.test.ts passes with a new case for duplicate names
RULES Change only OWNS paths. If you need another path, stop and report it.
      Return: changed paths + the command you ran + its result. Nothing else.
```

Refuses (non-zero) if the selected task lacks `owns` or `acceptance`. Prints `NOTHING TO DO` plus the reason when everything is blocked, done, or waiting on a decision. **This output is the entire dispatch prompt** — the orchestrator passes it verbatim.

### `airlock start <id>` / `done <id> --evidence "<text>"` / `block <id> --reason "<text>"`
State transitions. `done` requires evidence. `block` requires a reason. Both stamp timestamps.

### `airlock ask <id> "<question>" --options "a|b" --assume a`  ·  `--blocking`
Creates a decision and returns its id. **Default mode is `assume`**: `--assume <option>` is required, the task stays runnable, and `next` briefs the worker with the assumed answer. `--blocking` is the exception — it sets `mode: block`, marks the task `needs-you`, and is only legal for the five cases in §4.1.

`airlock answer D1 "read-only"` sets `status: answered`. If the answer differs from `assumed`, the CLI prints every task in `consumedBy` and exits non-zero with `REWORK REQUIRED` plus their ids, so the orchestrator re-opens them instead of silently leaving wrong work in place.

## 4.1 Run-until-truly-blocked

**Rule: the orchestrator never stops to ask while any task remains runnable.** Questions accumulate in the plan; the user is interrupted once, at the end, with all of them at once.

A decision may be `--blocking` **only** when one of these holds. Everything else takes `--assume`:

| Truly blocking | Why no default is safe |
|---|---|
| Irreversible or destructive (data deletion, force-push, migration on real data, prod deploy) | Cannot be undone by answering later |
| External commitment (send, publish, purchase, notify a third party) | Leaves the repo; not revertible |
| Missing access (credential, environment, account) | No amount of work proceeds without it |
| Rework cost > 2 tasks and the options are genuinely balanced | Guessing costs more than waiting |
| The goal itself is ambiguous — `done` cannot be made testable | There is nothing to build yet |

Everything else — naming, ordering, styling, which of two equivalent libraries, read-only vs editable, error-copy wording — is `--assume` with the recommendation. The assumption is recorded, the work proceeds, and the user confirms or overturns it at the end.

**Loop behaviour.** `next` selects in this order: (1) tasks with no open decision at all; (2) tasks under an open `assume` decision, briefed with the assumed value; (3) nothing. It reaches `NOTHING TO DO` only when every remaining task is `done`, `blocked` on a real failure, or waiting on a `block`-mode decision. `NOTHING TO DO` is the **only** point at which the orchestrator addresses the user.

**The single interruption.** At that point the orchestrator presents one consolidated set — open `block` decisions first, then assumptions to confirm — as one multiple-choice prompt (`AskUserQuestion` on Claude Code, its equivalent on OpenCode), each with its recommendation pre-selected. Answering it releases the remaining work and the loop resumes without a new session.

**Unattended.** `airlock next --unattended` additionally refuses to emit any task under a `block` decision and exits 2 with `PARKED: D1, D3`, so a scheduled run terminates cleanly with the questions queued rather than hanging on a prompt no one will see.


### `airlock status`
One screen, always this shape:

```
GOAL  Promo price table supports by-product rows        4/8 done
NEEDS YOU
  D1  Prod migration on live promo rows?   (blocks T7)  recommend: dry-run first
ASSUMED (confirm at the end)
  D2  Read-only or editable Value column?  assumed: read-only   used by T4
DOING
  T5  Wire provider state                  builder/sonnet   12m
BLOCKED
  T4  By-product row rendering             waiting on D1
NEXT
  T6  Add regression test                  builder/haiku
```

Empty sections are omitted. Nothing is written to disk — this is a view.

### `airlock audit <id>`
`git diff --name-only` for the working tree (or a named range) against the task's `owns`. Prints in-scope and out-of-scope paths; exits non-zero if anything is out of scope. Optional `--revert-out-of-scope`. Post-hoc, git-based, host-agnostic — this is the entire safeguard surface, and it catches shell-script writes the 2.x hook never saw.

### `airlock render [--md]`
Optional. Emits a markdown snapshot for a PR description or a handover. Generated on demand, committed only if the user wants a record. Never a source of truth.

## 5. Roles — three files

Each ≤ ~800 bytes. No lifecycle vocabulary, no gate taxonomy, no host specifics.

**`roles/builder.md`** — implements one task under its brief; may read and investigate within `owns`; writes tests where behaviour changes; simplifies what it just wrote before returning; stops and reports if it needs an unowned path; returns changed paths, the command run, and the actual result.

**`roles/checker.md`** — read-only. Verifies the task's `acceptance` against the current diff and the supplied evidence, not against the builder's narrative. Reports pass/fail plus what it could not verify. Never edits.

**`roles/browser.md`** — read-only plus the project's browser MCP. Preflights auth; if the browser or session is unavailable, stops and reports the exact refresh command. Never reads console/network logs wholesale; never echoes token-bearing URLs.

Model is **not** in role frontmatter. It comes from the task row, passed per dispatch. Three roles × four risk bindings replaces the ten agent files of 2.x.

## 6. Host shims

**Claude Code — `commands/airlock.md`:**

> Run `node scripts/airlock.mjs next`. If it prints NOTHING TO DO, show that and stop.
> Otherwise dispatch the printed block verbatim to the role it names, using the model it names, via `Agent`.
> On return: `airlock done <id> --evidence "<command + result>"`, or `airlock block <id> --reason "<cause>"` if it stopped.
> Then run `airlock audit <id>`; if it exits non-zero, block the task and report the out-of-scope paths.
> Repeat until NOTHING TO DO or the task budget is reached. Do not stop to ask anything while a task is still runnable — record open questions with `airlock ask ... --assume <default>` and keep going.
> Then print `airlock status` and put every open decision and every unconfirmed assumption to the user in **one** multiple-choice prompt, recommendations pre-selected. Feed the answers back with `airlock answer` and resume if any task became runnable.
> Report only: one line per completed task, the status table at the end, and that single prompt. Never narrate your own reasoning or work in progress.

**OpenCode — `.opencode/command/airlock.md`:** byte-identical except `task` replaces `Agent` and the model comes from the configured subagent matching the role.

That is the complete per-host surface. No policy, no adapter, no translation layer.

## 7. Token budget

| | 2.5/2.6 | 3.0 target |
|---|---|---|
| Standing prompt (commands + orchestrator + lifecycle) | 78,408 B | **≤ 5,000 B** |
| Per dispatch | full role file + restated contract | one `next` block, ~500 B |
| Per boundary | ledger read (up to 48K tokens observed) | `status`, ~400 B |

Enforced by test: the sum of `commands/`, `roles/`, and the shims must be ≤ 5,000 bytes LF-normalized. Same mechanism as 2.5's ceiling, an order of magnitude tighter, and achievable because the plan lives in a file the model never reads.

Archive rather than delete: `docs/airlock/archive/2026-08/` keeps 2.x specs and reviews for provenance.

## 9. Migration

`airlock import <ledger.md>` — one-shot, best-effort: reads a 2.x ledger, maps Crossings to tasks, `Owns` to `owns`, gate rows to `acceptance`, and the Resume checkpoint to task statuses. Prints what it could not map and exits non-zero if anything is ambiguous, so the user fixes it once by hand rather than inheriting silent drift.

## 10. Acceptance criteria

1. `airlock init` refuses a plan without testable `done`; `airlock next` refuses a task without `owns` or `acceptance`.
2. A 5-task delivery completes on **Claude Code** with one `/airlock` invocation, ≤6 dispatches, and no file edited outside its task's `owns` (verified by `audit`).
3. The same plan file completes on **OpenCode** with no changes to the plan and no host-specific code beyond the shim.
4. Standing prompt surface ≤5,000 bytes, asserted by test.
5. Killing the session mid-task and re-running `/airlock` resumes correctly from the plan file with no context reload.
6. A parked decision blocks only its dependent tasks; the run continues elsewhere and surfaces the decision in `status`.
7. `airlock audit` detects an out-of-scope write made via a shell redirect — a case the 2.x hook missed.
8. A 5-task run containing two `--assume` decisions and one `--blocking` decision interrupts the user **exactly once**, at `NOTHING TO DO`, with all three in a single prompt.
9. Answering an assumption against its `assumed` value exits non-zero with `REWORK REQUIRED` naming every `consumedBy` task.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Model does not call the CLI reliably | `next` supplies the brief the model needs, so calling it is the path of least resistance. A missed call is visible (task stuck in `doing`); mis-edited prose was silent |
| Losing pre-flight blocking loses real protection | Deliberate, user-ranked trade. `audit` gives post-hoc detection; Cupcake can plug in later without Airlock knowing |
| One-file state becomes a merge conflict in parallel lanes | One plan per delivery, not per repo; parallel tasks require disjoint `owns`; worktree-per-lane keeps diffs apart |
| CLI becomes the new sprawl | Hard cap: 7 verbs. A new verb requires deleting one |
| Assumptions compound into a large wrong build | `--assume` is illegal past the §4.1 rework threshold; `consumedBy` bounds the blast radius and `REWORK REQUIRED` makes it explicit rather than discovered later |
| Everything gets marked `--blocking` to be safe | `ask --blocking` requires naming which of the five §4.1 cases applies; the CLI rejects it otherwise |

## 12. Build order

1. CLI + schema + invariants + tests (the whole product is here)
2. Three role files; delete the ten
3. Two host shims; delete hooks, the 2.6 plugin, and the external launcher
4. `import` migration; run it on one real 2.x ledger
5. Prompt-surface ceiling test at 5,000 bytes
6. Dogfood: build 3.0's own follow-up work with 3.0, on both hosts

Ship when criteria 2 and 3 both pass on real work — the same plan file driven to completion on each host.
