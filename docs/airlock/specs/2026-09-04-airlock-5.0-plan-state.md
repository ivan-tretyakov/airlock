# Airlock 5.0 — Uncommitted Plan State

- Date: 2026-09-04
- Status: ready-for-agent
- Series: Airlock 5.0, spec 1 of 3. Independent of spec 2 (`2026-09-04-airlock-5.0-run.md`) and spec 3 (`2026-09-04-airlock-5.0-removals.md`); may be delivered first or in parallel with spec 2.
- Decided in: grill-me session 2026-09-04 (Q5, Q9, Q10, Q18)

## Problem Statement

The plan file is committed with every task and lands in every merge request. Once the work is merged the plan has no value, yet it stays in history and shows up in review diffs. Reviewers see plan churn beside product changes, and a repository that does not use Airlock still inherits the file when a plan-driven branch is merged.

A checker that only reports cannot finish today: `done` refuses a task with no changed files, and anything written under `.airlock/` is invisible to the audit. So a verification task has to invent a file to own in order to complete.

## Solution

The plan lives at `.airlock/plan.json`, excluded from git per clone through `.git/info/exclude`, and is never staged. Every other authority is unchanged: one commit per task with the `Airlock-Task` trailer and evidence, the ownership audit, dependency scheduling, decisions.

A checker task may complete with no product changes. `done` then records an empty commit carrying the same trailer and evidence so the durable record is intact and dependency lookups keep working.

## User Stories

1. As a developer, I want the plan to stay out of git, so that merge requests contain only product changes.
2. As a developer, I want the plan to live inside the worktree, so that it disappears with the worktree when the work is merged.
3. As a developer, I want the exclusion to be per clone, so that no `.gitignore` change lands in a repository that does not use Airlock.
4. As a developer, I want `init` to create the plan and the exclusion in one step, so that the first task boundary is clean without manual git work.
5. As a developer, I want existing repositories with a committed plan to keep working, so that in-flight plans are not broken by the upgrade.
6. As a reviewer, I want each task to remain one commit with a trailer and evidence, so that the history is still readable per task.
7. As a checker author, I want a checker task to complete without owning a product file, so that verification tasks are not padded with placeholder documents.
8. As a coordinator, I want a completed checker to leave a commit with its evidence, so that the `Airlock-Task` trailer lookup a later checker relies on still finds it.
9. As a developer, I want `start` to keep refusing a dirty product worktree, so that the boundary between tasks stays trustworthy.
10. As a developer, I want `status` and `render` to work from the new location without flags, so that day-to-day use does not change.
11. As a developer, I want a plan that was placed by `--plan` anywhere in the repository to behave the same way, so that multi-plan repositories are not special-cased.
12. As a developer, I want a clear error if `.git/info/exclude` cannot be written, so that a plan is never silently committed.

## Implementation Decisions

- Plan discovery order becomes `.airlock/plan.json`, then the two legacy locations, repository root and `docs/airlock/`. `init` writes to `.airlock/plan.json` unless `--plan` is given.
- `init` appends `.airlock/` to `.git/info/exclude` when that line is absent, and no longer commits the plan. In a worktree, `.git` is a file pointing at the common dir; resolve the exclude path through `git rev-parse --git-path info/exclude`.
- One staging rule replaces the unconditional plan staging: the plan file is staged and included in the task commit only if git already tracks it. An untracked plan is never added. This keeps legacy committed plans behaving as in 4.x and keeps new plans out of history with no schema change.
- The plan schema stays `airlock.plan/v4`. Nothing in the file changes.
- The coordinator-path rule is unchanged: the plan and `.airlock/` are ignored by the clean-boundary check and by the audit.
- `done` for a task whose role is `checker` and whose audit finds no in-scope paths records an empty commit with the same subject, `Airlock-Task` trailer, and `Evidence` trailer. Builder and browser tasks keep the existing refusal, since a builder with no changes is a failed task.
- The plan's `diffLines` for such a completion is zero, so the review budget is unaffected.
- The commit failure path is unchanged: on failure the plan file is restored and the task returns to `doing`.
- The `Airlock-Task` dependency lookup, which reads git log by trailer, is unchanged and is the only durable record once the plan is deleted with the worktree.

## Testing Decisions

- A good test drives the CLI as a subprocess against a temporary git repository and asserts on git state and CLI output, never on internal functions. The existing suite already does this through its `run` and repository fixture helpers.
- Tests to add, at that seam: `init` creates the plan under `.airlock/`, adds the exclude line once, and leaves the tree with no commit and `git status` clean; a full next → start → done cycle produces a commit whose tree does not contain the plan; a legacy plan committed at the root is still staged with the task commit; a checker task with no changes completes with an empty commit that carries both trailers; a builder task with no changes is still refused; `init` in a linked worktree writes the exclude into the common git dir.
- Prior art: the tests named "init state does not poison the first task boundary", "next, start, audit, and done create an audited task commit", and "checker uses the exact dependency trailer and excludes plan churn".

## Out of Scope

- The headless runner, routing, and the `EVIDENCE:` worker output contract (spec 2).
- Removal of hosts, `--host`, the OpenCode bootstrap, and the Herdr extension (spec 3). This spec must not touch the bootstrap code, even though `init` is edited; the bootstrap is deleted whole in spec 3.
- Migrating an existing committed plan to the new location. Legacy locations keep working; a developer who wants the new behaviour moves the file and removes it from git by hand.
- Any schema bump.

## Further Notes

The two specs after this one assume the staging rule above. Spec 2 assumes a checker can finish with an empty commit so the runner can complete a passing review task. Keep the diff small: discovery order, exclude line, one staging predicate, one role-conditional in `done`.
