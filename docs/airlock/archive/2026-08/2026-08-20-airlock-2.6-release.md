# Airlock 2.6 — OpenCode as a guard-capable Full-work host

**Version:** 2.6.0 · **Date:** 2026-08-20 · **Status:** implemented, NOT merged — blocked on the fixes in §5
**Baseline:** 2.5 (merged, PR #4 `00d6200`) · **Design:** `docs/airlock/specs/2026-08-19-airlock-2.6-opencode-guard-design.md` · **Review:** `docs/airlock/reviews/2026-08-19-airlock-2.6-review.md`

---

## 1. What 2.6 does

Until 2.5, Full work ran on Claude Code only, because the PreToolUse guard hook is a Claude Code mechanism. Every Airlock guarantee on OpenCode was prose. 2.6 makes OpenCode a **guard-capable host**.

The central decision: **the OpenCode plugin shells out to `hooks/guard.mjs` rather than reimplementing policy.** One policy engine, one file to change a rule, no chance of the two hosts drifting on what `ownedPaths` means. The adapter's only job is input translation.

### Components

| File | Role |
|---|---|
| `.opencode/airlock-guard-core.mjs` | Contract discovery, OpenCode→guard input mapping, `apply_patch` path parsing, guard subprocess invocation |
| `.opencode/plugins/airlock-guard.js` | `tool.execute.before` over `edit`, `write`, `apply_patch`, `bash`, `task`; exposes the `airlock_guard_status` tool |
| `scripts/opencode-guard.test.mjs` | 6 tests: inert-without-contract, root/worker mapping, shell+task restrictions, `apply_patch` path and move tracking, worker attribution |
| `commands/start.md` | Host harness gate rewritten from "Claude Code only" to **guard-capable** |
| `opencode.json` | `permission: { airlock_guard_status: allow }` |

### The host gate

Full work runs only on a guard-capable host. Claude Code qualifies when its PreToolUse hook is loaded; OpenCode qualifies only when `airlock_guard_status` reports `fullCapable: true`. Anything else is **BLOCKED — never downgraded to Compact, never executed inline**, and no user override bypasses a failed capability check.

## 4. Field incident (2026-08-19) — why this release is blocked

A real `/airlock-ship` on OpenCode with GPT-5.6 Sol ran **1h 6m and produced nothing**:

> BLOCKED before D0 execution. Airlock guard rejected ledger creation via `apply_patch` and requires an unavailable Edit or Write tool.

**Root cause.** `guardInputsForOpenCode` throws for any `apply_patch` touching a ledger path, and it is called **unconditionally** — not gated on a contract being active. So on OpenCode, `apply_patch` can never write a ledger, ever. `ship` must create the ledger. If the agent's toolset lacks `edit`/`write` — the normal case for Codex-family models, which prefer `apply_patch` — there is no path forward, and the denial names a tool the actor does not have.

**Why Claude Code never hit this.** Claude Code has no `apply_patch`. `hooks.json` matches exactly `Edit|Write|NotebookEdit|Agent|Task`, and the string `apply_patch` appears zero times in `guard.mjs`. Ledger hygiene was written entirely against tools whose resulting content the guard can see, so the "I can't simulate this, so I deny" branch never had to exist.

**The generalisation, and the reason for §6.** Airlock enforces by *prediction* — it inspects a call before it runs and infers what it will do. Prediction requires understanding every tool, on every host, in every shell. That surface is unbounded, and because prediction fails closed, every gap is a work-stopper. The same shape produced F1 (agent-type names), F3a (contract root under OneDrive), R1 (actor identity), and R2 (shell language).

**Related gap, opposite direction.** Ledger hygiene screens only `Edit`/`Write`/`NotebookEdit`. A `cat > docs/airlock/ledger/x.md` via Bash bypasses it entirely — on **both** hosts. The rule is simultaneously too strict to let work proceed and too loose to hold.

## 5. Blocking fixes before merge

| ID | Severity | Fix |
|---|---|---|
| **D0** | 🔴 | **Ledger `apply_patch` deadlock.** Map an `*** Add File:` block on a ledger path to a `Write` (its added lines *are* the new content) and let `guard.mjs` run the normal checkpoint/line-cap check. `*** Update File:` gets a conservative fallback. Never deny a ledger write outside an active contract. |
| **D1** | 🔴 | **`actorMode: single-actor` is defeated.** The plugin denies whenever a contract is active and attribution is unavailable, but `single-actor` exists precisely for hosts that cannot attribute — under it, worker rules apply to everyone and attribution is irrelevant. Neither new file reads `actorMode`. |
| **D2** | 🔴 | **`bash` mapped by host platform, not shell language.** `process.platform === "win32" ? "PowerShell" : "Bash"` routes bash command strings into the guard's PowerShell analyser on Windows — different tokenizer, wrong write-detection vocabulary. Always map OpenCode `bash` → `Bash`. |
| **D3** | 🟡 | **Contract validation is reimplemented** in `activeV2Contract` and checks less than `validV2Contract` does. When they disagree, the adapter blocks work the guard would allow — the inverse of the guard's documented fail-open. Export one predicate and import it. |
| **D4** | 🟡 | **Per-call waste.** `actorForSession` re-fetches an immutable `parentID` on every covered call; `runExistingGuard` spawns a Node process per call, and `apply_patch` spawns one **per file path**. Memoize actor per session; batch or short-circuit patch paths. |
| **D5** | 🟡 | **No denial may name a tool the actor does not have.** Check availability; if the alternative does not exist, allow and record rather than deadlock. |
| **D6** | 🟡 | **Flip the wrapper to fail open on its own runtime errors** (log loudly), matching `guard.mjs`. A missing Node install should not block all work. |
| **D7** | ⚪ | **Document the divergences**: ledger-patch restriction, fail-closed runtime behaviour, and the exact five-tool coverage. Assert in `plugin-policy` that the covered-tools list matches the documented one. |
| **D8** | ⚪ | **`airlock-doctor`**: one command that runs a real dispatch on a scratch repo on the current host and prints what is and is not enforced. Would have caught D0 in five minutes. |
| **D9** | ⚪ | **Live verification + Windows suites.** Confirm `fullCapable: true`, actor resolves, worker out-of-contract write denied, owned-path write succeeds, `task` denied under `allowDispatch: false`. Also check whether the plugin-level `worktree` (captured at init) matches the session directory when Airlock uses git worktrees — the status tool reads `context.worktree` while the hook uses the closure. |

## 6. Direction for 2.7 — enforcement by audit, not prediction

D0–D2 are symptoms of one design choice. The durable fix is to stop predicting:

1. **Process artifacts are never deniable.** Ledger, STATUS, plans, specs: verify integrity *after* write, report or auto-correct, never block. Nothing is protected by stopping the orchestrator writing its own notes.
2. **Replace pre-flight path contracts with post-dispatch diff audit.** After each worker returns, `git status --porcelain` + diff against `ownedPaths`; revert or surface out-of-scope changes. Tool-agnostic, host-agnostic, no adapter — and strictly stronger, since it catches the Bash writes the current guard misses.
3. **Keep pre-flight denial only where post-hoc is too late**: push/publish, `reset --hard`/rebase/`branch -D`, credentials, external mutations. Small, stable, enumerable, tool-vocabulary-independent.
4. **Pair with worktree isolation.** One worktree per lane makes the diff audit trivial and makes cross-lane contamination physically impossible.

Under that model the OpenCode adapter largely disappears rather than needing D1–D9.

## 7. Process rules adopted with this release

- **A release is not a daily driver until one real Full deliverable has completed on it end-to-end.** 2.6 was used unmerged and unverified; the review asked for exactly this check and it was skipped.
- **No new deny path without an `airlock-doctor` test.** The 80K prompt ceiling was the right instinct applied to size; apply it to enforcement surface too.

## 8. Recommended interim posture

Run **2.5 on Claude Code** for real work. Keep 2.6 on a branch until D0–D2 and D8–D9 are done. OpenCode Full work is an experiment that is not ready; OpenCode as a dispatched external worker under the 2.2 launcher contract remains fine and unaffected.
