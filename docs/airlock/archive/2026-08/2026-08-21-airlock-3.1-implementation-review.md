# Airlock 3.1 — Implementation Review

**Resolution (2026-08-21):** Addressed in the 3.1 working tree. Both shims now pass an explicit host on every lifecycle command; OpenCode catalog validation applies to version 1 and 2; tests use isolated per-repository config and generated-agent paths; offered pins expire after five minutes and `status` reports an unexpired pin; `AIRLOCK_NOW` is marked; first-run errors name `airlock config`; and `init` prints missing route commands. Regression coverage drives the OpenCode lifecycle through completion and reproduces each blocker.

**Date:** 2026-08-21 · **Reviewed:** uncommitted working tree on `main` (8 modified files)
**Baseline:** 3.0.1 at `16b0e38` · **Against:** `docs/airlock/specs/2026-08-21-airlock-3.1-routing.md`
**Method:** working tree staged and reproduced on Linux/Node 22; the suite executed; twelve adversarial probes run against real git repositories with synthetic route configs. Every finding below was reproduced.

---

## Verdict

**The routing engine is correct — I verified the window semantics, pinning, prune safety and fail-closed paths myself. Three blockers sit around it, and two of them are the same shape: a check that exists but is wired to the wrong condition.**

The suite reports 30 tests. **27 pass, 2 fail, 1 skipped** in a clean environment. Both failures are pre-existing regression guards that passed at 3.0.1 — they pass on the development host only because they read the developer's personal config file.

## 1. Verified working

Reproduced independently, not read from the test names.

**UTC window semantics are exactly right.** With a `peak` window of `06:00-10:00` on weekdays over a `prov/base` default:

```
05:59 -> prov/base · high      (before the window)
06:00 -> prov/peak · low       (inclusive start)
07:30 -> prov/peak · low
09:59 -> prov/peak · low
10:00 -> prov/base · high      (exclusive end)
Sat 07:00 -> prov/base · high  (day filter honoured)
```

**`--prune` is safe.** I orphaned one agent, then deleted the `peak` route from config while an active pin referenced its agent. Prune removed the true orphan and **kept** the pin-referenced agent. That is the exact protection §6.4 asked for.

**Other confirmed behaviours:** `CLAUDE_CODE_SUBAGENT_MODEL=opus` → `CLAUDE_CODE_SUBAGENT_MODEL overrides Airlock routing; unset it before dispatch`. Missing generated agent refused at `next`, not at dispatch (P4 satisfied). Project-agent shadow detection present (`airlock.mjs:463`). `airlock config` writes `version: 1` for a static route (P6 satisfied). Claude shim carries *"Do not pass a model parameter"* (P2 satisfied). Generated agent files carry `model`, `variant`, and the role body intact. Pin held across a window boundary for a `doing` task.

## 2. Blockers

### F1 — 🔴 The OpenCode shim's `start` omits `--host opencode`, so the OpenCode loop cannot advance

`.opencode/command/airlock.md` calls `airlock next --host opencode`, then `airlock start <id>` — with no host. `host` defaults to `flags.host ?? process.env.AIRLOCK_HOST ?? "claude"`, so `start` resolves, validates and pins the **Claude** route. Reproduced:

```
$ airlock next --host opencode
TASK T1 · builder · prov/peak · low
AGENT airlock-builder-prov-peak-low
$ airlock start T1                       # exactly as the shim writes it
missing generated claude agent: .../airlock-builder-haiku-medium.md; run airlock config --sync --host claude
$ airlock start T1 --host opencode       # what it should be
STARTED T1
```

On a machine that runs OpenCode and not Claude Code there is no `~/.claude/agents/` at all, so every task dies at `start`. The same omission applies to `audit`, `done` and `block`, which produces a second symptom: the OpenCode pin is never released.

```
$ airlock block T1 --reason x
BLOCKED T1: x
pins: ['opencode:airlock.plan.json:T1']       # leaked
$ airlock block T1 --reason y --host opencode
pins: []                                       # correctly released
```

**Fix:** add `--host opencode` to `start`, `audit`, `done` and `block` in the OpenCode shim — or, cheaper on the prompt budget, have the shim set `AIRLOCK_HOST=opencode` once, since the CLI already reads it. Add a test that drives the full loop with the shim's literal command forms.

The Claude shim has the same structural omission and is saved only by `claude` being the default. Worth making explicit there too, so the default is not load-bearing.

### F2 — 🔴 Catalog validation only fires on version 2, so the default configuration gets none

§3.4 says 3.1 *"writes version 1 while every route is static"* and that *"Version 1 may carry the additive top-level OpenCode variant catalog; Airlock 3.1 uses it to validate static OpenCode routes."* The code checks `routes.version === 2` before consulting the catalog (`airlock.mjs:385-387` in `routeFor`, and again at `758-760` in `config`). Reproduced with a version-1 config whose effort is deliberately nonsense:

```
$ airlock next --host opencode
TASK T1 · builder · openai/gpt-5.6-luna · TOTALLY-BOGUS
AGENT airlock-builder-openai-gpt-5-6-luna-totally-bogus     # accepted

$ airlock config --sync --host opencode
GENERATED  .../airlock-builder-openai-gpt-5-6-luna-totally-bogus.md
```

and the generated file:

```yaml
---
description: Airlock builder on openai/gpt-5.6-luna at TOTALLY-BOGUS effort.
mode: subagent
model: openai/gpt-5.6-luna
variant: TOTALLY-BOGUS
---
```

Flip the identical file to `"version": 2` and it is correctly refused: *"OpenCode model openai/gpt-5.6-luna does not declare variant TOTALLY-BOGUS in local catalog."*

So the check works — it is simply gated on the wrong thing. OpenCode resolves `variant` only when the model declares that exact name (`session/prompt.ts:654`), so a bogus or merely wrong-for-this-model variant silently falls back to the provider default. **This is the precise hole the catalog was introduced to close, left open for the configuration every user starts with**, and it defeats acceptance criterion 11 for static routes.

A second-order effect: `mergeRoutes` sets `version = Math.max(base.version, override.version)`, so whether OpenCode effort gets validated depends on whether *any* config file happens to be version 2. Validation should not be a function of schema version.

**Fix:** gate the catalog check on `host === "opencode"`, not on version. Add the F2 repro as a test at version 1.

### F3 — 🔴 Two pre-existing regression guards now fail in any clean environment

```
not ok 5  - init state does not poison the first task boundary
not ok 20 - unborn repositories use normal Airlock boundary behavior
```

Both use `bareProject()`, which — unlike `project()` — writes no routes to `.git/airlock/models.json`. 3.1 made `start` resolve and pin a route, so both now fail:

```
$ airlock start T1
missing local route for claude/builder/light; configure it with airlock configure
```

**Both passed at 3.0.1 in this same container** (26 tests, 25 pass, 0 fail). They pass on the development host because a real user-level `~/.config/airlock/models.json` exists there and satisfies the lookup. Two consequences:

1. **`npm test` is not hermetic.** It is green on the author's machine and red on CI, a fresh clone, or a colleague's box. The Windows run recorded in the 3.0.1 resolution gave real confidence; a run that reads the developer's personal config does not.
2. **The guards stopped guarding.** Test 5 is the R1 regression guard (init state poisoning the first boundary) and test 20 is the N4 guard (unborn repositories). Both now assert "a route exists" instead. If someone reintroduces R1, these tests fail for the wrong reason — or pass on the author's machine while R1 is broken.

**Fix:** default `AIRLOCK_CONFIG_DIR` to a per-test empty directory inside `run()` unless a test overrides it, and give `bareProject()` the same project routes `project()` writes. That makes every test hermetic and will surface any other silent dependency.

Credit where due: the sync tests **do** isolate correctly via `OPENCODE_CONFIG_DIR`, `AIRLOCK_CLAUDE_AGENT_DIR` and `AIRLOCK_CONFIG_DIR`, so `npm test` does not scribble into the developer's real agent directories. That was the failure mode I expected to find and it is properly handled.

## 3. Major

### F4 — 🟠 A pin on a merely-offered task never expires, and `status` contradicts it

`next` pins on offer. A task offered inside a window and started after it closes still dispatches the closed window's route:

```
07:30  next   -> prov/peak · low     ROUTE PINNED · peak
11:00  start           -> dispatches prov/peak · low       # window closed at 10:00
11:00  status -> "T1  do T1   builder/prov/base · PREVIEW"  # disagrees
```

§5.1's intent is stability across the seconds between `next` and `start`. In practice a `todo` task holds its pin indefinitely — and unlike a `doing` task it has no release path, since only `done` and `block` clear pins. So acceptance criterion 6 (*"a new task changes routes exactly at configured UTC boundaries"*) is false for any task offered before a boundary and started after it. Meanwhile `status` previews at current time and prints a route that is not the one that will be dispatched — and `status` is what the user reads at the single consolidated prompt.

**Fix, either:** expire a `todo` pin at the end of its matched window (or after a short TTL), so a resumed run re-resolves; **or** stop pinning at `next`, pin at `start`, and have `start` emit the authoritative brief. The second also removes the `status`/`next` disagreement structurally, because there is only ever one selection point.

Whichever is chosen, `status` should show the pinned route for a pinned `todo` task rather than a preview that contradicts it.

## 4. Medium

**F5 — 🟡 `AIRLOCK_NOW` is honoured in production with no explicit marker.** `AIRLOCK_NOW=2030-01-01T00:00:00.000Z airlock next` returns `ROUTE PINNED · default · evaluated 2030-01-01T00:00:00.000Z`. The override is detectable only by noticing an implausible timestamp. For a release whose entire claim is deterministic, auditable routing, either restrict the variable to tests or print an explicit `CLOCK OVERRIDE` line.

**F6 — 🟡 The first-run error names a command that does not exist.** `missing local route for ...; configure it with airlock configure` — the command is `airlock config` (`airlock.mjs:376`). Carried over from 3.0.1, but 3.1 makes it fire on `next` as well as `start`, so it is now the first thing a new user sees.

**F7 — 🟡 Nothing bootstraps routes.** 3.0.1's `init` seeded `.airlock/models.json`; 3.1 localised routes and `init` now seeds nothing, so a fresh install fails on every command until the user hand-writes a config file. `init` should print the exact `airlock config --host <h> --role <r> --risk <k> --model <m> --effort <e>` lines needed for the roles and risks actually present in the plan. This is the same first-run gap R1 was about, in a new form — fail-closed is right, silent-and-undirected is not.

## 5. Token efficiency and wasted cycles

**Prompt surface 3,844 B against the 5,000 B ceiling** — up 230 B from 3.0.1 for the `AGENT` line, the no-model instruction and `--unattended` plumbing. Correct trade; the ceiling test still holds.

**CLI 44,936 → 57,946 B (+29%); tests 24,795 → 29,630 B (+19%).** The test growth is smaller than the source growth for the first time across 3.0–3.1, which is what F3 is a symptom of: two of the new behaviours (host-scoped lifecycle, version-1 catalog validation) have no test at all, and they are exactly the two blockers.

**The cost lever this release exists for does not fully engage yet.** F2 means a static version-1 OpenCode config generates agents whose `variant` OpenCode silently discards — so per-role effort routing, the actual saving, may not be applying at all in the default setup. F1 means the OpenCode side cannot run to completion. Neither burns tokens directly; both mean the release does not yet deliver the efficiency it was designed for.

**Wasted cycles:** F1 is a hard stop at `start` — no stashing, no partial work, so it is cheap to discover and cheap to fix. F4 is the one that silently produces wrong-but-plausible work (an expensive route used when a cheap one was configured, or vice versa).

## 7. Note on the work

The window resolver, pin lifecycle, prune protection and fail-closed paths are all correct on first submission, which is the hard part of this release. All three blockers are wiring, not design: a missing flag in a prompt file, a condition on `version` instead of `host`, and a test harness reading real user config. The pattern from the 3.0 rounds holds — the mechanisms are right and the blast radius or the trigger condition is what needs narrowing.

One structural observation worth carrying forward: F2 and F3 are both cases where **the thing that would have caught the bug is the thing that was skipped.** The catalog check exists but never runs at version 1; the two failing tests exist but no longer test what they claim. Both would have been caught by running the suite in a clean environment, which is now the single highest-value addition to the release gate.
