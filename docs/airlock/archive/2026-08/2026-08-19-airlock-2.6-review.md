## Verdict

**The architecture is right and the 2.5 follow-ups all landed. Four defects to fix before merge — two of them defeat enforcement paths this release exists to create.**

The central decision — the OpenCode plugin **shells out to `hooks/guard.mjs` rather than reimplementing policy** — is the correct one and the reason this release is reviewable at all. One policy engine, one place to change a rule, no chance of the two hosts drifting on what `ownedPaths` means. That is worth the process cost of the subprocess call.

## Recommendations

### R1 — 🔴 `actorMode: "single-actor"` is defeated on OpenCode

`airlock-guard.js` denies unconditionally when a v2 contract is active and actor attribution is unavailable:

```js
if (active && !actor) throw new Error("Airlock contract active: OpenCode actor attribution is unavailable, so this operation is denied.");
```

But 2.4 added `actorMode` precisely for hosts that cannot distinguish actors: under `single-actor`, `guard.mjs` applies worker rules to everyone and attribution is irrelevant. Neither `airlock-guard-core.mjs` nor the plugin reads `actorMode` (confirmed: no occurrence in either file). So on any OpenCode host where `session.get` fails or `parentID` is unavailable, a `single-actor` contract — the documented escape hatch for exactly this situation — still blocks every covered tool call.

**Fix:** read `actorMode` in `activeV2Contract`. When it is `single-actor`, skip attribution entirely and pass `agent_id` (worker rules apply to all). Only demand attribution under the default `agent-id` mode. Add a test asserting a `single-actor` contract permits an owned-path write with attribution unavailable.

### R2 — 🔴 The `bash` tool is mapped by host platform, not by shell language

```js
tool_name: process.platform === "win32" ? "PowerShell" : "Bash"
```

OpenCode's `bash` tool executes bash-syntax commands; the host OS does not change that. On Windows this routes a bash command string into `guard.mjs`'s **PowerShell** analyser, which uses a different tokenizer (backtick escapes, doubled single quotes) and looks for `Set-Content`/`Add-Content`/`Out-File`/`New-Item` rather than bash redirection semantics. Two failure modes, both real on your primary machine:

- **missed denials** — a bash `cat > out-of-contract.ts` tokenized under PowerShell rules may not be recognised as a write;
- **false denials** — PowerShell-specific parsing on bash syntax can resolve operands it should not, and the guard denies unresolved shell writes by design.

**Fix:** always map OpenCode's `bash` tool to `tool_name: "Bash"`. Reserve `"PowerShell"` for a genuinely PowerShell-executing tool if one is ever added. Add a Windows-gated test asserting the bash mapping does not change with `process.platform`.

### R3 — 🟡 Contract validation is reimplemented and can disagree with the guard

`activeV2Contract` re-parses the contract and checks only `schema`, `ownedPaths`, and `expiresAt`. `guard.mjs`'s `validV2Contract` additionally validates `root`, `processPaths`, `allowDispatch`, and `actorMode`, and **fails open when the contract is invalid**.

The two can therefore disagree: a contract that `guard.mjs` rejects as malformed (→ allow) may be "active" to the adapter (→ demand attribution → deny). The adapter then blocks work the policy engine would permit — the opposite of the fail-open contract the guard documents. This is drift of exactly the kind the shell-out architecture was chosen to avoid.

**Fix (preferred):** export the validation predicate from `hooks/guard.mjs` and import it in the core, so there is one definition. **Fallback:** mirror `validV2Contract` exactly and add a test that feeds the same malformed contracts to both and asserts identical activity verdicts.

### R4 — 🟡 Per-call session lookup and subprocess spawn: avoidable wasted cycles

Two costs on **every** covered tool call:

- `actorForSession()` issues a `client.session.get` round trip. A session's `parentID` is immutable, so this is a constant re-fetch of a constant.
- `runExistingGuard()` spawns a Node process (~30–80 ms cold start). `apply_patch` spawns **one per file path** — a 20-file patch is 20 process launches.

No token cost, but it is wall-clock waste on the hot path of every OpenCode session, and it grows with exactly the batched operations OpenCode encourages.

**Fix:** memoize actor per `sessionID` in a `Map` (with the failure case cached too, so a broken lookup does not retry per call). For `apply_patch`, batch all resolved paths into a single guard invocation — or, minimally, short-circuit on the first denial rather than resolving every path first. Both are small changes with no policy impact.

### R5 — ⚪ Document the deliberate divergences

Three behaviours differ between hosts and are currently discoverable only by reading the code:

1. **`apply_patch` may never touch a ledger** (`use edit or write`). Defensible — hygiene needs content to simulate — but it means an identical task succeeds on Claude Code and is denied on OpenCode.
2. **Runtime failures fail closed** on OpenCode (missing Node, non-zero guard exit → throw), while `guard.mjs` fails open for *contract* problems. The split is sound; it should be stated, because it means a broken Node install blocks all work rather than silently disabling enforcement.
3. **Coverage is exactly five tools** (`edit`, `write`, `apply_patch`, `bash`, `task`). Any other file-mutating tool OpenCode gains later is unguarded by default.

**Fix:** one "Harness divergences" section in `adapters/opencode/README.md` and the spec, listing all three. For (3), also add a `plugin-policy` assertion that the covered-tools list in the plugin matches the list documented in the README, so adding a tool without updating coverage fails a test.

### R6 — ⚪ Verify `fullCapable` end-to-end on a real OpenCode host

`airlock_guard_status` is now a **gate**: Full work proceeds on OpenCode only when it reports `fullCapable: true`. The 6 unit tests exercise the core mapping, not the plugin's live behaviour under OpenCode's runtime. Before relying on it:

1. Run a real OpenCode session with a v2 contract; confirm `airlock_guard_status` returns `fullCapable: true` and `actor` resolves (not `"unresolved"`).
2. Confirm a worker's out-of-contract `write` is denied, and its owned-path `write` succeeds.
3. Confirm `task` is denied for a worker under `allowDispatch: false`.

Record the results in the ledger. Also worth checking during that run: whether the plugin-level `worktree` captured at init matches the session directory when Airlock uses git worktrees — the status tool reads `context.worktree` while the hook uses the closure `worktree`, and if those can differ, contract discovery resolves from the wrong root.

Also unchanged from prior releases: all five suites green on **Windows** before the PR.

## Cost note

Cycles: unchanged by design — 2.6 adds enforcement, not workflow. The only new recurring cost is R4's per-call session lookup and subprocess spawn, which is why R4 is worth doing now rather than later.

Tokens: **flat (+8 bytes)** — the first release in four that did not grow the prompt surface, and the ceiling test now makes that structural. Headroom is 1,592 bytes; the next release that adds a section will need to remove one.

## Note for the record

Shelling out to `hooks/guard.mjs` instead of porting it is the decision that makes OpenCode Full-work support maintainable: policy stays in one file, and the adapter's job is reduced to input translation — which is exactly where R1–R3 sit, and why they are all small fixes rather than redesigns.
