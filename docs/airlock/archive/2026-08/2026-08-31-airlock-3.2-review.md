## Verdict

**Request changes.** The guidance has the right cost-control objective, but the PR does not yet identify itself as Airlock 3.2, and two parts of the authoring policy can lead users to produce contradictory or invalid plans.

| Priority | Finding |
|---|---|
| P1 | The PR does not produce an Airlock 3.2 release |
| P2 | The checker guidance contradicts itself |
| P3 | `standard` is described as a schema default, but no default exists |

## Findings

### P1 — The PR does not produce an Airlock 3.2 release

The npm package, Claude plugin manifest, and marketplace entry still declare version `3.1.0`:

- `package.json:3`
- `.claude-plugin/plugin.json:4`
- `.claude-plugin/marketplace.json:12`

The README installation command also remains on tag `v3.1.0`, and the migration text describes Airlock 3.1. An `npm pack --dry-run --json` identifies the artifact as `airlock@3.1.0`.

If this branch is intended to be the Airlock 3.2 release PR, update all release manifests and installation or migration documentation together. If it is only a documentation precursor to a later release branch, the PR should not be presented as the 3.2 release itself.

### P2 — The checker guidance contradicts itself

`PROJECT-CONVENTIONS.template.md:13` says not to add a checker task for any `light` or `standard` builder work. Line 15 then permits a per-task checker whenever acceptance cannot be captured in one command, regardless of risk. The consolidated-checker recommendation on line 14 does not say whether it applies to the light and standard tasks excluded by the preceding rule.

This leaves at least two reasonable but incompatible interpretations for a standard task whose acceptance is not a single command: checker tasks are forbidden by line 13, but explicitly permitted by line 15.

State the exception directly. For example: builder-run acceptance is sufficient for light and standard tasks when one command captures acceptance; otherwise use one consolidated checker where possible. Reserve per-task checkers for complex or critical tasks and explicitly named exceptions.

### P3 — `standard` is not an actual schema default

The new guidance says the default `risk` is `standard`, but `validatePlan` requires every task to contain a valid explicit `risk` and rejects a missing value (`scripts/airlock.mjs:152`). The existing README also correctly says that every task requires risk.

Change the guidance to “Default to `standard` when authoring a task” or implement a real schema default. The former matches the apparent intent and avoids implying that Airlock fills in an omitted field.
