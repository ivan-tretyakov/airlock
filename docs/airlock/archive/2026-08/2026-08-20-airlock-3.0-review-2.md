## 2. New blocker

### N1 — 🔴 `block` and `audit --revert-out-of-scope` destroy the user's entire stash stack

`preservePaths` (airlock.mjs:490-494) ends with:

```js
git(root, ["stash", "push", "--include-untracked", "--message", message, "--", ...paths]);
const commit = git(root, ["rev-parse", "refs/stash"]).trim();
git(root, ["update-ref", ref, commit]);
git(root, ["update-ref", "-d", "refs/stash"]);   // ← deletes the whole stack, not one entry
```

`refs/stash` is not "airlock's stash" — it is *the* stash ref for the repository. Deleting it discards every entry the user had, along with the reflog that makes them reachable. Reproduced:

```
$ git stash list                  # before
stash@{0}: On main: USER-WIP-2
stash@{1}: On main: USER-WIP-1
$ airlock block T1 --reason "stray"
BLOCKED T1: stray
$ git stash list                  # after
                                  ← empty
$ git reflog show refs/stash
fatal: ambiguous argument 'refs/stash': unknown revision
```

The commits survive as unreachable objects until the next `gc`, recoverable only via `git fsck --unreachable` — which no one thinks to run, and which airlock's own retained refs are explicitly designed to survive but these are not.

This is strictly worse than R6. R6 deleted the file the user was warned about; N1 silently destroys work the user deliberately saved and that has nothing to do with the task. It fires on the two most common recovery paths, so it will be hit by anyone who uses stashes at all.

**Fix — one line.** Replace `update-ref -d refs/stash` with `git stash drop --quiet`, which pops only the entry just pushed. Verified:

```
$ git stash push --include-untracked -m airlock -- new.txt
$ git update-ref refs/airlock/test $(git rev-parse refs/stash)
$ git stash drop -q
$ git stash list
stash@{0}: On main: USER-2
stash@{1}: On main: USER-1     ← preserved
$ git cat-file -t refs/airlock/test
commit                          ← airlock's ref intact
```

Add a regression test that asserts `git stash list` is unchanged across a `block`.

## 3. New major

### N2 — 🟠 Blocking one task under `--parallel` steals the other task's in-flight work

`block` preserves `dirtyProductPaths(root, planPath)` — **the entire dirty worktree** — rather than the task's own scope. R12 just made `--parallel` usable, so these two fixes collide. Reproduced with T1 owning `a/` and T2 owning `b/`, both `doing`:

```
$ airlock block T1 --reason "stray"
BLOCKED T1: stray
$ git status --porcelain
 M airlock.plan.json            ← b/f.js is gone
$ git show --name-only refs/airlock/blocked/T1/<ts>^3
STRAY.md
a/f.js
b/f.js                          ← T2's work, swept into T1's stash
```

T2 is still `doing` and its builder is still running. It returns to a worktree where its own edits vanished; `audit T2` then sees nothing and `done T2` commits an empty delta with evidence claiming success. That is the R3 failure class — a wrong answer rather than a stuck one — re-entering through a different door.

**Fix:** scope the preserve to the blocked task. Stash `task.owns` matches plus out-of-scope paths not claimed by any other `doing` task; leave everything else alone. If that set cannot be computed unambiguously (glob overlap), refuse to block while another task is `doing` and say so, rather than sweeping.

## 4. Remaining medium

### N3 — 🟡 A goal-level blocking decision blocks nothing

`ask --blocking --case goal` now works, but records `blocks: []`, so `next` keeps dispatching:

```
$ airlock ask --blocking --case goal "Is the goal testable?" --options "yes|no"
ASKED D1
$ airlock next
TASK T1 · builder · haiku       ← still building
```

§4.1 defines this case as "there is nothing to build yet". An open `case: goal` decision should make `next` return `NOTHING TO DO / Waiting on D1` regardless of task state — otherwise the one blocking case that means *stop everything* is the only one that stops nothing.

### N4 — 🟡 A repository with no commits fails with a raw git error

`start` in a freshly-`git init`-ed repo surfaces git's own message:

```
fatal: ambiguous argument 'HEAD': unknown revision or path not in the working tree.
```

`dirtyProductPaths` diffs against `HEAD` unconditionally. Wrap it: treat a missing HEAD as "everything is new" and emit an Airlock-shaped message.

### N5 — 🟡 `next` silently swallows unrecognised arguments

The Claude shim forwards `$ARGUMENTS`. If the user types `/airlock fix the login bug`, the CLI receives `next --host claude fix the login bug`, ignores the four extra positionals, and dispatches whatever task was next — with no warning that the request was discarded. Given the shim's `argument-hint` is `[--unattended]`, an unknown positional should be an error, not silence.

### N6 — 🟡 `status` prints `(blocks )` for plan-level decisions

Cosmetic, one line, but it appears in the one consolidated prompt the user actually reads.

### N7 — 🟡 The OpenCode path depends on an unpublished package

README correctly says the `airlock` bin must be on `PATH` via global install or `npm link`. The package isn't published, so `npm link` in the checkout is the only real route, and it silently doesn't exist on a second machine. Either publish, or have the OpenCode shim fall back to an absolute path written by a setup step. This is the one remaining gap between "works when I dogfood it" and "works where it ships".

## 5. Token efficiency and wasted cycles

**Prompt surface:** 3,614 B, up 312 B from the shim gaining `${CLAUDE_PLUGIN_ROOT}` paths and `--unattended`. Still 28% under the asserted ceiling. Correct trade — the growth bought a shim that actually runs.

**Real token win this round:** checker briefs no longer carry the plan-file diff (R10). On a five-task plan with two checkers that is roughly 80 lines of JSON churn per checker dispatch removed, and it also stops the checker reasoning about bookkeeping.

**Wasted cycles:** three of the four session-killing deadlocks are gone and each has a regression test. N1 does not stall a run, so it costs no cycles — it costs the user's saved work instead, which is worse but cheaper in tokens. N2 costs a full task's rework plus a false-positive `done`.

**Code growth:** CLI 32,993 → 37,281 B (+13%), tests 8,712 → 16,923 B (+94%). Test-to-source ratio nearly doubled. That is the right direction for a file that is now the entire product.

## 7. Note on the fix quality

The resolution went beyond the letter of the findings in three places worth recording: `audit` now *prints* the recovery ref rather than merely creating it; `opencodeAgents` is validated at config-load time so a missing binding fails loudly instead of at dispatch; and the checker's dependency lookup escapes as well as anchors the trailer. The pattern in N1 and N2 is the same in both cases — a correct new mechanism applied with too wide a blast radius. Both are scoping bugs, not design errors, and neither argues against the approach chosen.
