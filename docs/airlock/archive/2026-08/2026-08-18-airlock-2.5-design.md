# Airlock 2.5 — Design Specification: Right-weight the dispatch

**Status:** approved design input (user-commissioned, 2026-08-18) — implementing session runs `/airlock:plan` from this spec; `brainstorm` is satisfied by this document.
**Baseline:** Airlock 2.4 as completed (uncommitted working tree, version 2.4.0, R1/R4 fixed). 2.5 assumes 2.4 has merged.
**Scope:** one theme — **the orchestrator over-buys**. Too many verification dispatches, and too-heavy leaves chosen for ordinary work. Both are prompt-level defects with the same shape: a rule pushes one direction and nothing pushes back.
**Sources:** observed OpenCode behaviour (verify leaf dispatched after most steps; `code-complex`/`code-critical` preferred for ordinary work), and the 2.4 tree read directly (`commands/plan.md`, `commands/ship.md`, `commands/start.md`, `agents/orchestrator.md`, `agents/code-*.md`).

---

## 0. Diagnosis

### 0a. Verification is over-dispatched

The rules are already correct; the practice over-fires.

- `ship.md` §3 is explicit that independent verification runs **"For the final Crossing"** — pack-level gates against the frozen candidate — while implementers supply their own focused RED/GREEN and Crossing-check evidence.
- But `plan.md:43-45` sizes a Crossing at 1–3 tasks of 2–15 minutes, so a Crossing ≈ a step, and `ship` is invoked at every Crossing.
- The gate table (`plan.md:105-107`) has an **Executor host role** column but no notion of *inline* execution, so every `required` gate reads as "dispatch somebody."
- Net effect: N Crossings × (implement + verify) instead of N implements + one verification pass.

**OpenCode amplifier.** `task` selects a configured subagent; if the project config declares a `verify` agent, calling it is frictionless and no guard exists to make anyone reconsider.

### 0b. Work class is over-escalated

Four rules push up; none push down.

| Cause | Location | Effect |
|---|---|---|
| "Ambiguity escalates one level" — unbounded, stated twice | `start.md:61`, `orchestrator.md:28` | Every task begins with some ambiguity, so the default drift is upward |
| Class definitions are descriptive, not testable | `plan.md:74-77` ("cross-cutting behavior", "public-contract") | Most changes touch >1 file; any exported symbol reads as a public contract |
| Budgets cap dispatch **count**, never **weight** | `start.md:67-69` | Escalation is free from the orchestrator's point of view |
| Class → model is hardcoded 1:1 | `code-complex.md`, `code-critical.md` = `opus` | No way to express "needs care, but sonnet suffices" |

Underneath: an asymmetric incentive. Under-classifying looks like negligence (a rule is violated); over-classifying looks like diligence (no rule is violated). Without a cost term, up is always rational. This is the same asymmetry that made everything Full before 2.4's release lane fixed it — the fix shape is the same: name a testable criterion and default down.

**Escalation also uses the wrong lever.** Uncertainty about *approach* is answered today by a heavier implementer; it should be answered by a cheap investigation. Only uncertainty about *blast radius* justifies a heavier leaf.

## WS-A — Right-weight the leaf (classification)

### A1. Bound the escalation rule (`start.md`, `agents/orchestrator.md`)

Replace "Ambiguity escalates one level" in both places with:

> Escalate one level only when you can **name the specific irreversible or cross-cutting surface** at risk, and state it in the classification line. If the uncertainty is about *approach* rather than *blast radius*, dispatch a cheap investigation (`investigate`, or a scoped `worker` read-only pass) instead of a heavier implementer. Unnamed uncertainty is not grounds for escalation.

The always-Full safety list (security, credentials, destructive, migrations, production/live, irreversible) is unchanged and still overrides everything.

### A2. Make the work classes testable (`plan.md:72-77`, mirrored in `LIFECYCLE.md` if the definitions live there)

Replace the four descriptive bullets with criteria plus a default-down rule:

- **Light** — single file or a mechanical, fully specified change with an obvious check.
- **Standard** — contained implementation with clear seams and tests. **This is the default.**
- **Complex** — meets at least one: touches ≥3 modules; changes a shared interface other code depends on; or the fix location is unknown at plan time.
- **Critical** — meets at least one: irreversible; touches credentials, secrets, or security boundaries; changes a published contract others consume; or is expensive to unwind.

> **If you cannot name which criterion is met, the class is Standard.** Record the named criterion in the route row; a route row claiming Complex or Critical without a criterion is an invalid plan row.

### A3. Add a weight budget beside the count budget (`start.md:67-69`, `orchestrator.md`)

> Dispatch **weight** budget, per Delivery Pack: at most **one** `code-critical` and at most **two** `code-complex` dispatches by default. Exceeding either requires one PROGRESS line naming the criterion from A2 that justifies it. Weight budgets are separate from, and additional to, the per-workflow dispatch-count budgets.

### A4. Decouple role from model (`plan.md` routing table, `agents/code-*.md`, dispatch protocol)

Pick the **leaf by role**, the **model by risk**, and pass the model per dispatch rather than inheriting it from the leaf's frontmatter.

- The host supports this: Claude Code's `Agent` accepts a per-call model, and OpenCode selects a configured subagent whose model is set in project config.
- `plan.md`'s existing "Selected host agent / Selected available model" mapping table becomes the authoritative record; the route row states class, leaf, and selected model as three separate facts.
- Change `code-complex.md` frontmatter default from `opus` to `sonnet`, and document that opus is selected per dispatch when the route row names a Complex/Critical criterion. `code-critical.md` keeps `opus` as its default.
- Constraint retained from 2.2: never route a leaf to Fable without fresh per-invocation user approval.

## WS-B — Right-size verification (gate execution)

### B1. Add an execution mode to the gate table (`plan.md:105-107`)

Add one column, `Executed by`, with exactly three values:

| Value | Meaning | Cost |
|---|---|---|
| `implementer` | The implementing leaf runs it inside its own dispatch and returns the evidence | zero extra dispatches |
| `orchestrator-inline` | The orchestrator runs the command itself between dispatches | zero extra dispatches |
| `independent` | A separate verifier/reviewer leaf runs it against the frozen candidate | one dispatch |

Rule to state alongside the table:

> Deterministic checks — unit tests, typecheck, lint, build — are `implementer` or `orchestrator-inline` by default. `independent` is reserved for judgment gates (pre-ship code review, visual fidelity, browser-functional) and for any gate on the **final** Crossing of a pack. A per-Crossing gate marked `independent` requires a one-line reason in the row.

### B2. State the pack-level default explicitly (`ship.md` §3, `plan.md`)

`ship.md` already scopes independent verification to the final Crossing; make it unmissable:

> Independent verification is **pack-level by default**. Intermediate Crossings ship on implementer evidence plus the orchestrator's own deterministic checks. Do not dispatch a verifier per Crossing unless the plan's gate row says `independent` with a stated reason.

### B3. Reviewer bundle already covers the cost of the remaining review

No change — 2.4's `build-review-bundle.mjs` means the one pack-level review no longer re-crawls the repository. B1/B2 reduce the *number* of such dispatches; the bundle reduces the *cost* of each.

### B4. OpenCode guidance (`adapters/opencode/README.md`)

> For Compact and Full-lite work, do not declare a `verify` subagent in project config. If the role is unavailable, the orchestrator runs deterministic checks itself, which is the intended behaviour. Declare `verify` and `review` only for projects that actually run pack-level judgment gates.

## WS-C — Tests and docs

- `plugin-policy.test.mjs`: assert the bounded-escalation wording, the "cannot name a criterion → Standard" rule, the weight-budget sentence, the `Executed by` column with its three values, and the pack-level verification default. Assert `code-complex.md` declares `sonnet`.
- `README.md`: one short "Right-weighting" section — class criteria table, weight budget, and the three gate execution modes. Glossary additions: `Executed by → who runs the check`, `weight budget → how many expensive workers per package`.
- `PROJECT-CONVENTIONS.template.md`: one line telling projects to record their deterministic check commands, so `orchestrator-inline` has something exact to run.

## Acceptance criteria

1. A plan for a 3-Crossing pack produces **≤1** `independent` gate row, and intermediate Crossings carry `implementer`/`orchestrator-inline` gates only.
2. A route row claiming Complex or Critical without a named criterion fails review as an invalid plan row.
3. An ordinary contained change classifies **Standard** and dispatches `worker` or `code-standard` — not `code-complex`.
4. A pack exceeding one `code-critical` or two `code-complex` dispatches emits the PROGRESS line naming the criterion.
5. All four suites green on Windows; `plugin-policy` covers each new rule.
6. Dogfood: this spec ships through the release lane (Compact PR, user merge as the gate).

## Measurement

Reuse the 2.4 gate — no new instrumentation. Expected per Full deliverable of N Crossings: **~3N dispatches → ~N+1**, with opus confined to rows naming a criterion. Record in the first weekly `ai-usage.py` reading after merge: dispatch count per pack, the share of dispatches on the expensive tier, and the count of weight-budget-exceedance PROGRESS lines. If the expensive-tier share does not fall while exceedance lines are frequent, A3's budget is nominal — tighten the limit before adding further rules.

## Risks

| Risk | Mitigation |
|---|---|
| Under-verification on genuinely risky work | The always-Full safety list is untouched; pack-level independent review still runs; `independent` remains available per Crossing with a stated reason |
| `sonnet` default for `code-complex` degrades hard work | The route row can still select opus per dispatch; A2's criteria make the "this is genuinely Complex" case explicit rather than reflexive |
| Weight budget becomes a rubber stamp (PROGRESS line every time) | Measurement above catches it: if the expensive-tier share doesn't move, the budget is nominal — tighten it |
| Criteria get gamed ("touches ≥3 modules" satisfied trivially) | Criteria are recorded in the route row and visible at review; a pattern of thin justifications is a review finding, not a silent cost |

## Out of scope

Launcher hardening (still usage-gated, 2.6+); per-worker parallel contracts; OpenCode guard-equivalent port; any change to the always-Full safety list or to contract v2 enforcement.
